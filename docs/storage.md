# 存储、配置路径与发现

## 已确认的职责划分

对应 [需求基线](requirements.md) R-18、R-20 至 R-23。

| 内容 | 权威性 | 默认位置 |
| --- | --- | --- |
| 项目规则、对象、范围、link 与理由 | 持久权威元数据，文本记录 | `<project-root>/.omd/`，可改到任意指定目录 |
| 本机项目/外置目录映射、全局默认值 | 用户配置，不是图数据的第二份权威来源 | 配置根 |
| SQLite 查询索引 | 可删除重建 | 缓存根，不放项目目录 |
| 用于差异定位的原始内容基线 | 必须能在没有 Git、没有缓存时恢复 | 持久位置/布局待定，建议元数据根下 snapshots |

“元数据是文本”不意味着二进制基线必须伪装成文本。基线字节与 JSON/TOML 等元数据记录应区分。

## 配置根与缓存根

Linux 的已确认优先级：

```text
OMD_CONFIG_PATH
  → 有效的 XDG_CONFIG_HOME 下的 omd/
  → ~/.config/omd/

OMD_CACHE_PATH
  → 有效的 XDG_CACHE_HOME 下的 omd/
  → ~/.cache/omd/
```

Windows/macOS 同样优先 OMD 专用环境变量；没有覆盖时再用各自标准配置/缓存目录。

OMD 变量暂按“直接指定 OMD 完整目录，不再附加 omd/”理解。变量为空、相对路径、无效或不可访问时的行为尚未由用户确定，见 Q-10。XDG 对自身变量的要求不能自动当作 OMD 变量的既定契约。

配置路径覆盖与某项目的元数据位置选择是两件事：修改 `OMD_CONFIG_PATH` 不自动迁移项目 `.omd/`，修改 `OMD_CACHE_PATH` 不改变持久权威数据。

## 候选目录布局

以下是工程建议，具体文件名、字段、JSON 拆分和 schema 版本尚未冻结：

```text
<metadata-root>/
  omd.toml                  格式标识、项目/alias、默认编码、工作流配置
  records/                  资源、范围、关联的结构化文本
  changes/                  首次建立、变更及确认理由
  snapshots/                差异/未解决关联仍引用的原始内容基线

<config-root>/
  projects.toml             本机 project_root ↔ metadata_root 映射

<cache-root>/
  <project-id>/
    <instance-key>/
      index.sqlite          派生索引
```

`project-id`、`instance-key`、单实体文件/资源分组文件都只是候选设计。它们不依赖 Git worktree/branch。必须防止多个本地副本共享缓存后读到不属于本次输入的结果。

### 不引入双主同步

推荐写入权威文本，再使 SQLite 索引匹配该版本。SQLite 不保存唯一一份理由、确认版本或必需基线。索引删除后能够恢复全部持久含义。

反复只读检查不应为了“最后检查时间”重写权威记录。真实的标记更新可以产生 diff；目标是消除格式噪声，不是隐藏实质变化。

### 原始基线与清理

hash 用于判断内容不同，不能恢复旧内容供 Myers 对比。OMD 需要自己保存或完整重建已登记内容，不从 Git blob 取得必要基线。

建议按内容寻址复用快照，只清理不再被活跃标记、关联复核或必要记录引用的内容。存多久、是否保存全部历史、二进制如何归档由 Q-09 决定；不要未经需要扩成完整版本控制系统。

## 外置映射与 alias

本地外置映射暂表达为：

```text
project_root  = 用户被跟踪项目的实际目录
metadata_root = 组织该项目关联的权威记录目录
```

这两个路径是本机解析信息。元数据中的 `proj:A:file_path` 不应被强行替换为某台电脑的永久绝对路径。

alias 名称及来源属于组织图的元数据目录；如何结合本地路径解析见 Q-03。外置记录若未同步，别人复制代码并不会自动获得这份图，这不是 SQLite 缓存重建能弥补的。

## 元数据目录发现

已确认：默认 `.omd/`；不用默认名时，支持在项目根直属子目录识别 OMD 特定结构，不全仓库递归搜索。

建议优先级：显式 metadata path → 本机注册映射 → `.omd/` → 单层候选。建议用专用 manifest 标识而非仅凭 `records/` 等普通目录名猜测。多个候选报歧义；明确指定路径损坏则报错，不悄悄换另一套图。

这些优先级和 manifest 仍是 Q-10。项目根识别与单层元数据发现必须分开；核心不借 Git 才能找根。

## 单写者与版本冲突

已确认：禁止并发更新；依据的旧 hash 与当前版本不符则报错，不自动合并。

工程建议：同一元数据根内的写锁覆盖“读取当前版本 → 比较 expected hash → 持久写入”的关键区间。只有先校验 hash、随后才加锁不能避免两个写入者同时通过检查。

hash 校验的精确对象、锁文件位置、旧锁恢复、多文件更新的中断恢复、源文件在检查途中又改变的处理见 Q-09。单写者约束不意味着可以阻止外部编辑器修改源文件，也不意味着多文件更新天然原子。

允许主动 import `.omd/` 的约定不变；实现不能为了让自跟踪收敛而隐藏这些文件或自动确认自身写入。
