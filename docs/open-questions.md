> **状态（2026-09-18）：** Q-01 至 Q-12 已全部在 [openspec/changes/define-tracking-contracts](../openspec/changes/define-tracking-contracts/design.md) 中解决或收窄为工程默认。本文件保留为历史问题清单，各条的最终决定以 design.md 的 D-01 至 D-21 与 ED-01 至 ED-19 为准。实施期待定清单集中记录在 design.md 的"当前收敛程度"一节。

这些问题保留给本机后续设计/实现工具，不是本次代替所有者做出的选择。主逻辑已收敛，不需要重新讨论 Rust、三态、Git 独立性、JSON args 或 stdout/exit 0。

## 必须在相关行为实现前明确

### Q-01 范围迁移与变脏条件

**已由 D-01、D-16、D-17 解决：** 纯位置变化给候选迁移+显式复核，不自动保持确认；文件 hash 变化后 verify 用 Myers 只标脏受影响的 range commit；range 身份是 commit 链而非坐标。剩余：边界插入/删除/拆分时的等价映射报告是实现期算法细节。

- 只在范围前插入内容，范围自身未变：自动迁移还是显式确认？
- 范围开头/结尾插入的内容是否包含在标记内？删除或拆分如何表达？
- 同一内容多次出现、diff 有多个等价映射时如何报告？
- 文件 hash 变化后是按受影响范围变脏，还是更保守的策略？

已确认：不证明语义无害；标记更新需理由；三态不增加。可提出机械迁移/批量确认，但尚未批准自动放行。

### Q-02 确认作用域与关联传播

**已由 D-03、D-04、D-07、D-08、D-14、D-17 解决：** 逐步传播，处理 A↔B 不影响 A↔C 的待处理义务；link 只连接 range commit；允许成环，截断终止；unclean 平面列出全部（D-21）。

场景：A 同时关联 B、C；使用者处理 A↔B 后，A↔C 是否仍需处理，记录如何避免互相覆盖？A→B→C 中只改 A 时，间接影响到什么深度？

需定义标记与 link 复核的关系、双方版本依据、传播方向与类型、环处理、批量确认清单。不能只更新文件 hash 就让未处理关联消失。该约束不等于已决定引入多套生命周期。

### Q-03 alias、内容位置与版本

**已由 D-06、D-21 解决：** alias 绑定本地目录当前内容；remote 身份可显式登记映射；不匹配时 verify 报错，用户显式更新别名登记解决（force 已取消）。跨项目 link 走 range commit。

已确认 alias 命名空间、`proj:A:file_path`、`proj:root:file_path`，以及示意来源 `git:github.com/someprojectpath`。

待定：

- alias 如何映射到用户已 import 的本地目录？
- 是否提供可选获取适配器；如果有，何时显式取得远端内容？
- 检查当前内容，还是明确登记的快照？
- 外部项目不可读时如何展示；反向查询搜索哪些已知元数据存储？
- alias 重命名、指向变更、同一路径多种来源如何保留身份？

不从一个示意 `git:` 标识推导自动 clone、Git 必需依赖或远端可用保证。

### Q-04 import 的持续范围

**已由 D-02、D-16、D-17 解决：** import 持续计入覆盖率统计范围（不是只登记当时清单）；全量递归含子目录；exclude/include 层叠调整，语法参考 .gitignore；import 不直接管理文件或 range。

用户手动 import 一个目录后，是持续管理该目录未来的文件，还是只导入当时清单？这决定新增文件是否自动呈现为空。

同处需要定义递归范围、显式排除、删除/重命名/复制、重叠 import 的对象身份。

不能重新打开的决定：未 import 不纳管；允许主动 import `.omd/`；follow 符号链接。

### Q-05 command 执行上下文

**已由 D-05、D-16 部分解决：** command 是虚拟文件对象，commit init 建立，verify 时按 VERIFY_COMMAND_AUTO_RUN 配置（默认 false）和 `--run-command` 参数决定是否运行。cwd、stdin、env、超时、输出限额、信任边界等收在 design.md 实施期待定清单（Q-05 余量）。

已确认：固定 executable + JSON 字符串数组，只跟踪 stdout，必须 exit 0。

待定：执行发生在 import、检查还是显式刷新；读取他人配置与运行程序的信任边界；Git hook 是否触发已注册 command；cwd、stdin、环境继承、PATH/绝对路径、超时、输出限额；输出编码与 byte 模式的引用表达。

建议针对一次捕获的完整输出进行确认，不为 hash 校验反复运行程序。固定 args 不需要扩展成动态模板系统。输出截断不应伪装成完整成功结果。

### Q-06 工作流规则表达

**已由 D-17 解决：** 命名检查集合，`commit tag` 给文件夹/文件打 tag，`omd rule 单向/双向 link <tag> <tag2>` 约束 tag 间 link 方向，`--level=warn|fail` 默认 fail。规则基于 tag 而非具体文件。

CLI 如何增删查改检查用例？持久配置如何表达类型、方向、目标项目/目录、关系数量、覆盖阈值、提醒/失败、启停？检查是命名检查集还是带合法转移的阶段状态机？

规则功能已确认；复杂状态机、通用脚本断言和插件系统没有被确认。跳过就是显式参数/手动关闭，不发展成自动豁免制度。

R-27 已确认 programming-thinking 的 Lean 范围必须直接关联 UML 源码和实际实现；该要求不再待决。待细化的是如何在通用规则中表达范围/关系类型与缺口诊断，不是是否需要双侧 link。模型证明先完成、实现待补时的报告不得混同完整闭环，也不得新增标记状态。

## 可由工程方案提交默认值并形成测试

### Q-07 完整引用文法与坐标边界

**已由 ED-01 至 ED-04 与 D-17 解决：** 0-based 左闭右开区间；换行/BOM 按原文保留；编码由用户 CLI 参数或配置指定；路径只存在 `/`；`::` 用 `\::` 转义。

文本计数已定为解码后 Unicode 字符，byte 为原始字节。待写清：行列索引起点、半开/闭区间、换行/BOM/tab、无效编码、编码默认值优先级、保留前缀转义、Windows 路径和 JSON 内的 `::`。不要全字符串盲目 split。

### Q-08 覆盖聚合

**已由 ED-05、ED-06 与 D-17 解决：** 重叠 range 按并集计算覆盖长度；脏判定按 commit 的 range 而非位置；分母为解码后总 code point 数；空文件覆盖率显示 100%。

三态已定，只有已确认算覆盖。待定义范围重叠如何归并、同一位置同时有脏/已确认标记如何显示、统计分母、文本空白规则、二进制按哪些字节范围统计、零内容结果及每种关系检查的计数作用域。

不增加"成熟度"维度，不承诺覆盖率代表文档充分性。

### Q-09 权威 schema、基线与写入恢复

**已由 ED-07 至 ED-12 与 D-11、D-17 解决：** TOML 每 commit 一文件；SHA-256 hash；盐字符集与时间戳格式已定；无独立 Myers 基线存储（diff 时用算法计算）；单写者 lockfile + manifest 崩溃恢复。

- TOML/JSON 的具体布局、ID、格式版本、迁移和序列化稳定性。
- Myers 所需旧字节如何持久保存、去重、回收；不只留 hash 或缓存。
- 旧 hash 前置条件作用于元数据、来源快照还是二者；如何避免读取/确认间的变化。
- 单写者锁、异常退出恢复、多文件提交中断、缓存失效/重建。
- 字节和字符差异策略、hash 算法、数据规模/时间内存预算。

禁止并发、hash 冲突即失败已定；不新增并发协作服务或自动合并。

可选 programming-thinking 还需明确验证证据的记录格式：如何关联实际 Lean 文件、依赖/工具链版本、命题与检查结果，以及 UML/实现两端的版本依据。先遵守 R-25/R-27/R-28 的证据与复核要求，不据此引入第二套权威存储或自动 Lean 语义依赖分析。

### Q-10 路径解析与元数据发现

**已由 ED-13 至 ED-15 解决：** 环境变量空值等同未设置；相对路径相对 cwd；不存在/不可写报错退出；项目根识别 `--root` > 向上 `.omd/` > 报错；非默认目录只扫直属一级子目录含 `omd-manifest.toml`。

OMD 专用环境变量优先已定。待细化：空值、相对值、错误路径处理，是否完整目录覆盖，项目根识别，manifest 识别结构，单层候选的优先级和歧义处理，本机注册文件 schema。

建议显式路径优先、损坏不静默回退、多候选报歧义，但这些还不是用户冻结的全部细节。

命令名称、JSON 输出 schema、错误代码、跳过参数、批量确认方式、安装/卸载 hook 与现有 hook 共存。hook 检查当前文件还是实际暂存内容需要说明，避免承诺超出其实际检查范围；任何 Git index 处理只属于可选适配，核心仍独立。
