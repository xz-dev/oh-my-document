# 候选架构与工作流

状态：模块拆分与实现流程是工程建议；[需求基线](requirements.md) 中的用户决定才是已确认约束。本文件不是冻结 API，也不含已实现代码。

## 产品组成

```text
人 / AI（使用 skills）
        │
        ▼
       CLI ◀── 可选 Git hook / 其他显式调用入口
        │
        ├── 来源解析与采集：文件文本、文件字节、固定命令 stdout
        ├── 内容 hash 与 Myers 差异
        ├── 标记、关联、确认理由
        ├── 覆盖与工作流检查
        └── 权威记录写入 / SQLite 派生索引
```

可选 Git hook 不负责提供变化清单。CLI 即便没有 Git，也能在手动 import 的范围内完成整个流程。

## 候选模块边界

| 模块 | 职责 | 不承担 |
| --- | --- | --- |
| 配置与项目上下文 | OMD 路径覆盖、外置映射、alias、已 import 范围 | 自动纳管所有目录、Git 必需根识别 |
| 来源层 | 读取文件/follow 链接，按明确触发采集命令 stdout | 富文档正文解析、动态参数语言 |
| 内容与基线 | 内容摘要、字节快照、解码映射 | 用 hash 还原原文、缓存成为唯一基线 |
| 差异与范围 | Myers 编辑定位、范围候选映射、歧义诊断 | 语义等价证明、静默猜测重绑定 |
| 关联与三态 | 范围关系、变更理由、空/脏/已确认 | 用 skip 伪造确认 |
| 规则运行器 | 按类型/目录/项目检查图约束与覆盖 | 接管编辑器、凭 AI 推理替代结构检查 |

## 候选数据概念

这些名称用于讲清设计，不代表最终表名、文件名或已冻结 ID 类型。

- **Source/Artifact：** 来源引用、内容解释方式、类型；文件或成功 command stdout。
- **Snapshot：** 某次观察到的原始内容及 hash；供比较和确认使用。
- **Anchor：** 绑定内容版本的范围，明确文本/字节坐标。
- **Link：** 两个范围的关联，可附类型并从两端查询。
- **Change/Confirmation：** 创建/修改/确认及理由、所依据内容版本。
- **CheckCase：** 作用范围、关系要求、覆盖要求、提醒/失败策略、显式启停。

唯一的用户可见标记生命周期仍是空、脏、已确认。命令失败、无法定位、hash 冲突是诊断原因或检查结果，不需要增设标记状态。

## 主流程

### 建立关系

1. 使用者显式 import 范围或注册相应来源；命令注册与执行许可见 Q-05。
2. 取得实际内容，建立可恢复基线。
3. 使用者选定两端范围与关系，给出首次建立理由。
4. 单写者校验其依据的版本后持久化。
5. 后续检查按三态与规则报告，不以“建过一个链接”证明内容质量。

### 发现变化

1. 在已纳管范围取得当前内容；文件变化不靠 mtime 或 Git diff 下结论。
2. 内容 hash 不同时，对旧内容与新内容作 Myers 对比。
3. 定位受影响范围，输出脏态原因或候选迁移结果。
4. 检查相关关系与覆盖规则，给出需要处理的对象。
5. 使用者更新内容/标记或说明关系保持不变；确认作用域见 Q-02。
6. 校验 expected hash 并保存结果；版本冲突报错，不掩盖冲突。

“只位置移动是否脏”“A 改了是否传到 C”“何时推进基线”是 Q-01/Q-02 的行为选择，不由上述概念流程暗中决定。

### 运行规则

已确认示例：

- 对 spec，要求上层 UML 关联与下层实现关联。
- 对一个语言实现目录，要求另一目录或项目中的方言实现关联。
- 对受管范围，要求有未过期的已确认标记。
- 对采用 programming-thinking 程序性证明的 Lean 范围，要求直接关联实际 UML 源码及实际实现范围，不能用间接路径或文件级泛链接充数（R-27）。

规则可以先定义再逐渐补齐。检查可提醒或失败；使用者可显式选择跳过/关闭某检查用例。是否还需要有状态阶段转移、如何表达规则、是否支持脚本化断言见 Q-06；当前没有承诺任意执行插件。

## 可选 Lean skill 与核心的分工

[programming-thinking 契约](programming-thinking.md) 已确认使用边界：由 skill 指导使用者选定 UML 细节，建立顺序逻辑模型与证明义务，运行 Lean 检查，按程序单元严格一一对应地翻译实现，并通过 CLI 保存双侧范围关联及复核理由。

Lean 在外部验证声明的模型性质；OMD 核心跟踪 `.lean`、UML 源码、实际代码及相关证据的内容版本和范围关系，不增加 Lean 必需依赖，不从 link 或验证日志自动推导语义正确。证明义务审查、依赖声明和实现对应审查属于使用者/skill，不承诺核心解析所有语言语义。

本 skill 不分析并发、多线程或 OMD 自身的锁正确性。可先交付模型证明而保留实现缺口，但完整交付须具备有效的双侧直接 link；它不是新增覆盖成熟度或第四种标记状态。

本阶段只写 skill 契约，不复制既有通用 skill，也不引入验证命令自动执行器。关系类型、规则配置与证据存储细节按 Q-06/Q-09/Q-11/Q-12 规格化。

## 确定性承诺的边界

相同的已捕获内容、规则、坐标约定和确认记录，应产生相同的工具判定。Myers 的选择与并列匹配策略也需固定并测试。

它不承诺：

- 外部 command 每次输出相同。
- 局部文本未变代表整体语义未变。
- 格式变化不会产生大量脏标记。
- 最短编辑路径代表用户实际编辑历史。
- 所有未知元数据目录里的跨项目反向关系都能自动发现。

## 错误处理原则建议

- 命令失败、缺少基线、无法解码、路径不可读、资源超限要显式诊断，不能当作内容没有变化。
- 重建 SQLite 不丢持久含义，也不悄悄执行 command。
- 符号链接跟随要能发现环并终止，不把环处理变成拒绝所有链接。
- 不擅自排除用户主动 import 的 `.omd/`；但不承诺自引用更新能够收敛。
- 一个关联未处理的问题不应因另一个关联确认而被文件级新 hash 覆盖掉；精确机制见 Q-02/Q-09。
