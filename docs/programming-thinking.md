# programming-thinking：受限的 Lean 建模与程序性证明

状态：项目所有者确认的 OMD skill 使用契约，先行写入设计文档；尚未交付产品 skill、Lean 模型、CLI 集成或已执行的证明。对应 [需求基线](requirements.md) R-24～R-28，验收见 [acceptance.md](acceptance.md) S-28～S-37。

## 1. 目的与定位

OMD 将提供可由用户或 AI 调用的 programming-thinking skill，用 Lean 分析 **已有 UML 细节中的顺序状态机、逻辑链与分支遗漏**。其产物是接近伪代码的预构建及其程序性证明，随后必须严格按证明过的结构一一对应地翻译为实际实现。

它不是把文档改写成另一种代码，也不是独立于 UML 和实现的第二份需求规格。使用顺序为：

```text
UML 源码中的具体状态、转移、条件与数据流
    → Lean 中明确的模型、契约与证明义务
    → Lean 检查通过的伪代码程度预构建
    → 严格一一对应的实际代码实现
```

上述箭头表达工作顺序；持久跟踪必须另外建立 **Lean↔UML 源码** 和 **Lean↔实际实现** 两组直接 OMD link，不能只保留间接路径。

该 skill 是可选工作流，不要求所有 OMD 用户安装 Lean，不自动把整个项目交给 Lean 管理。选择对某个范围采用程序性证明后，本文件的证明、翻译和关联义务才对该范围生效；不能只采用“已证明”的标签而不履行对应义务。

## 2. 何时使用，何时停止

### 适用前提

开始前，使用者必须指出：

- 实际 UML 源码文件及待分析的具体范围，而不是只有图片、聊天说明或文档标题。
- 已展开到可以讨论状态、事件、输入、守卫、转移、结果和错误分支的细节。
- 一个具体的正确性问题，例如“这些守卫是否覆盖全部合法输入”“拒绝分支是否仍可能进入成功态”“每步执行后是否保留不变量”。
- 输入域、初始状态、前置条件、环境假设及不在本次证明范围内的行为。
- 预期对应的实现范围；已有实现则定位实际源码，尚未实现则明确记录待落实的义务，不伪造目标。

只有架构总览、模块名或自然语言愿景时，先补齐 UML 细节；没有明确证明义务时，不为形式化而创建 Lean 文件。存在旧 Lean 文件不等于自动授权扩大本次证明范围。

### 明确排除

本 OMD skill **不得用于分析或证明并发、多线程任务**，包括调度、线程交错、锁、数据竞争、原子性、内存模型、并发死锁及并发生命性。遇到 UML fork/join、异步竞争或共享可变状态时，先判断正确性是否依赖这些语义；依赖则停止本 skill 的该部分分析，明确交给另选方法，不将任务强行串行化后宣称原并发任务已证明。

若并发系统内有可独立隔离的纯顺序子过程，可以只分析该子过程，但必须在 UML、模型及结论中明确隔离边界，不能外推至调用它的并发系统。OMD 自身的单写者锁、并发写入拒绝等仍需单独工程测试；证明顺序状态转移不等于验证锁实现。

这是 **本项目工作流的能力与适用范围限制**，不是宣称 Lean 语言在理论上不能表达并发。不得把原有通用 skill 中的并发建模、调度或公平性说明直接搬入此契约。

## 3. 什么才算程序性证明

先写证明义务，再写模型。模型至少应把选定 UML 细节落实成可审查的声明：

| UML 细节 | Lean 中需明确的内容 | 应检查的性质 |
| --- | --- | --- |
| 初始节点、输入 | 状态类型、输入域、初始化 | 前置条件可满足，初始化建立不变量 |
| 决策、守卫 | 条件及所有分支，包括非法输入处理 | 覆盖性；要求唯一选择时的互斥性 |
| 动作、状态转移 | 显式状态和数据变换 | 转移前提、保持性、禁止状态不可达 |
| 顺序控制流、逻辑链 | 中间状态、组合顺序 | 上一步后置条件足以满足下一步前置条件 |
| 错误/终止节点 | 错误结果、终止条件、后置条件 | 无遗漏错误路径；声称终止时确有相应证明 |

每个声称的性质必须有对应命题及证明。不能用类型能编译、一次成功执行、几个示例测试，或“读取者觉得模型像原文”代替证明。有限域穷举仅支持该明确有限域内的命题；局部转移保持性也不自动证明整个流程终止。

必须检查以下伪证明：

- 只有枚举、结构体和流程名称，没有证明义务。
- 定理只证明 `True`、定义自身，或与目标正确性无关的恒等式。
- 把希望证明的结论直接作为公理或前置假设；用无法满足的前置条件排除所有真实输入。
- 为了让证明通过，删掉 UML 中的失败分支、缩小输入域，或改变转移顺序，却不修订 UML 和说明理由。
- Lean 自己通过检查，但实际 UML 源码和实现与该模型无关。

出现这些情况时应明确报告未完成程序性证明，而不是增加注释或重复翻译来充数。建模发现的真实缺陷，应先反馈并修订 UML 契约，再同步模型与实现，不能为了保持旧文档而证明另一个更容易的问题。

## 4. 一一对应的实现翻译

对采用该 skill 的范围，以 **有程序语义的单元** 对应：状态、输入、守卫、转移、数据更新、成功/错误返回及其执行顺序。先在 UML 与 Lean 间核对，再把 Lean 预构建严格一一对应地翻译到代码，并逐项审查。

- 每个受证明的程序单元都要定位实际实现中的对应范围；实际实现中的受管分支也要能反查到 Lean 和 UML。
- 不得新增、遗漏、合并或重排影响行为的分支/步骤而沿用旧证明。需要不同算法、额外行为或控制流优化时，先更新 UML 与 Lean 并重新证明，再翻译和关联。
- 一一对应不是要求 Lean 的 tactic、辅助引理或语法行逐字生成生产代码。它们证明的是程序单元；辅助证明及依赖必须可追溯，不能通过链接无关代码假装每个引理都有运行时实现。
- 类型表示、数值边界、溢出、异常、I/O 契约和外部调用不能隐藏在“语言差异”里。若差异影响证明性质，先把相应约束纳入模型并验证；不能证明的部分明确列为范围外，不声称整个实现已证明。

Lean 内核接受的是模型中的命题，不会因为人做了翻译或 OMD 保存了 link 就自动证明另一语言实现正确。交付时须分开说明“模型已证明”“实现已逐项对应审查”“实现测试结果”；未对目标语言及翻译关系做机器证明，就不能称为端到端机器验证。

## 5. 必须通过 OMD 保存的双侧关联

每个作为程序性证明使用的 Lean 范围，必须同时具有：

1. 到 **实际 UML 源码范围** 的直接 link：能定位被建模的状态、条件、转移或数据流。渲染图片、README、文件标题或文件级泛链接不能替代具体源码对应。
2. 到 **实际代码实现范围** 的直接 link：能定位对应的程序单元。伪代码、未来路径、TODO、测试文件或验证日志不能冒充生产实现。

两类关系都需按 R-08/R-09/R-18 保存理由与有效的版本依据，并支持从任一端查询。同一个程序单元的 UML、Lean、实现应能逐项核对，而不是只证明“这个 Lean 文件各连了一个图文件和代码文件”。

证明依赖也要可追溯：定理依赖的类型、转移、守卫、辅助定义、导入及其版本必须纳入验证证据与影响复核。只标记定理语句却放任其调用的转移定义变化，不足以支持原结论。OMD 不承诺自动解析 Lean 的语义依赖图；使用者/skill 负责声明范围和依赖。

### 尚未实现时

允许先按 UML 完成 Lean 预构建及模型证明，这正是预构建的用途。此时明确列出缺少的实际实现及 link，按配置提醒或使完成检查失败，不能宣称三方闭环已完成。计划中的实现路径可以作为待办说明，但不能创建已确认的虚假实现关联来消除缺口。

### 内容发生变化时

UML、Lean、实际实现或证明所依赖的内容/工具链发生相关变化，都必须重新核对受影响的证明及对应关系，记录理由并重新验证。即使定理文本没变，依赖的转移或前置条件改变也不能沿用旧结果。

缺失、过期或未复核的任一必要关系都不能满足该 skill 的闭环验收。精确范围迁移和传播策略仍按 Q-01/Q-02 规格化，不在这里擅自规定整文件变脏或全图传递。

“模型证明完成但实现未就绪”是交付说明，不是第四种 OMD 标记状态。显式跳过/关闭检查仍遵循 R-17，但跳过不修复 link、不确认标记，也不允许继续宣称受影响范围已完成程序性证明交付。

## 6. 验证证据与完成条件

后续 skill 应指导使用者逐步完成：

1. 适用性检查：明确 UML 细节、顺序语义和证明义务；排除并发依赖。
2. 定义完整模型及命题，核对输入域、失败路径、不变量和假设，排除空洞或循环证明。
3. 使用项目指定的 Lean 工具链检查 **实际交付的 Lean 文件**；记录文件/依赖版本、实际命令、退出状态、诊断、通过的定理和精确证明范围。
4. 不接受 `sorry`、`admit`、未解目标或以未证明自定义公理冒充结果；检查顶层定理的公理依赖，例如 `#print axioms`，区分明确披露的基础逻辑信任与假设掉目标结论。不能以 `unsafe` 或未经审查的可信扩展支撑声称的结果。
5. 按受证明程序单元一一对应地翻译为实现，审查数值/错误/副作用语义并执行相关实现测试。样例执行可辅助检查，但不是证明的替代品。
6. 建立并复核 Lean↔UML、Lean↔实际实现的直接范围 link，记录理由与所依据版本；核对双向缺口。
7. 分别报告模型证明、实现对应审查、实现测试及 OMD 关联检查的真实结果和未验证范围。缺任一项，不报告完整交付。

工具链不可用、证明失败、实现不存在或 link 检查尚未实现时，如实记录阻塞/未完成项；不得编造检查结果。运行外部验证不意味着 OMD 读取配置或重建缓存时可以自动执行命令，执行许可仍遵守 Q-05。

## 7. 正反示例：区分证明与转写

以下只是契约示例，不是本仓库已有的 Lean 证明或产品测试。

适用例：UML 描述单次请求依次进行输入校验、权限判定和结果返回。Lean 显式建模合法/非法输入及允许/拒绝分支，证明守卫覆盖、拒绝不能进入成功态、顺序步骤的前后置条件衔接。实际函数按相同分支逐项实现，每个对应单元建立 Lean↔UML 与 Lean↔实现 link。

反例：把“校验→处理→返回”改写为 Lean 的三个构造器，输出一句“流程正确”，再链接一篇说明文档。没有相应命题、错误分支分析及实际实现关联，这是文档转写，不是程序性证明。

越界例：把多个线程对共享状态的更新写成一条顺序转移链并检查通过。该结果不能证明线程安全；本 skill 应停止并说明并发部分不适用。

## 8. 与原有通用 programming-thinking 的关系

本契约参考既有 skill 的模型/命题分离、实际 Lean 检查与假设披露原则，但 **不机械复制该 skill**，尤其不沿用以下做法：

- 以 Lean 作为全项目或所有讨论的全局唯一事实源。
- 仅因目录存在或以往用过，就在每次任意代码/文档更新后自动全面形式化。
- 以“可执行文档”定位代替与 UML、实际实现相对应的程序性证明。
- 将并发、fork/join、调度公平性或所有线程交错纳入本 skill。
- 用自然语言回译、独立读者认同或一次可运行输出代替证明及双侧关联。

本次只确定产品 skill 的适用范围与必须遵守的契约。安装目录、调用方式、OMD 关系类型名称、验证记录 schema 及具体 CLI 参数仍待工程规格化（Q-06/Q-09/Q-11/Q-12）；不提供假装已可执行的 `omd` 命令，不复制或修改用户现有通用 skill，也不为核心增加 Lean 强依赖。
