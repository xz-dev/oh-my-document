> **当前覆盖说明：** 本文件保留 R 编号和历史产品决定。`separate-range-identity-and-location` 已取代 R-10～R-12 中的复合 `proj:`/`command::`/`byte::` 输入形式；当前 CLI 使用独立路径、`--project`、`--range`、`--mode` 和封闭来源字段，见 [来源、内容与坐标](source-model.md)。历史示例不是当前使用说明；未改变的产品意图继续有效。

状态：核心要求已确认，边界规格未全部冻结。本文件整理自项目所有者的交互设计，不将调研建议当成用户决定。

与实现行为有关的未决项见 [open-questions.md](open-questions.md)。R 编号是需求追溯编号，不是新增产品语法。

## 定位与边界

### R-01 产品形态

项目名 `oh-my-document`，简称 `omd`。以 Rust 实现确定性变化跟踪与规则检查核心，提供 CLI 和指导 AI 使用工具的 skills。产品本身是可配置工作流，不只是被动链接索引，也不接管用户的编码中间层。

### R-02 结构化规划与逐步细化

支持从逻辑流程、系统组件关系到更细的设计，直至函数内部逻辑范围之间的关联。人类可指定细节，由 AI 继续细化；工具维护对象之间的联系。关联包括文档—代码、文档—文档、代码—代码、图—图，不限定单一层级。

### R-03 工具独立性

不绑定编辑器、AI agent、spec 工具或绘图工具。用户没有选型时推荐 OpenSpec 与 Mermaid，已有选型则沿用。它们的纯文本产物易于跟踪，但不是 OMD 核心运行条件。

### R-04 Git 独立性

变化发现依靠文件内容 hash；差异定位使用 Rust 内的 Myers 同类算法。不得依赖 `git diff`、Git changed-files、commit、index 或 blob 才能完成核心跟踪。普通文件夹也必须可用。有 Git 时，用户可以主动安装 hook 提醒或阻止遗漏更新；hook 是可选入口。

### R-05 不承担语义证明与富文档解析

OMD 核心不承诺自动证明格式变化无害、跨语言实现等价、文档解释充分或理由在业务上合理。工具确定性跟踪内容与处理记录，人或 AI 负责语义判断。可选 programming-thinking skill 可调用 Lean 证明显式模型中的性质（R-24～R-28），不使核心变成语义证明器，也不自动证明目标语言实现等价。

需要按正文跟踪 Word 等富文档时，在外部转成 Markdown 等文本；核心不解析 DOCX 内部 ZIP/XML。显式字节模式可跟踪文件原始字节，但不等于格式适配。原文件与转换文本的双向同步不在已确认范围。

## 管理、来源与关联

### R-06 显式 import

只有用户手动 import 的文件夹才纳管。发现 OMD 配置不等于纳管全部项目。主动 import `.omd/` 允许，不做特殊禁止或隐藏排除。import 后新增文件如何处理见 Q-04。

### R-07 符号链接

follow 符号链接，关注目标文件内容。循环/断链须有工程处理，但不得偷换为默认不 follow。

### R-08 外置范围标记与理由

在源内容之外保存范围与范围的 link，不要求往源代码/文档塞标记。支持记录 source 起止位置与 target 起止位置。首次建立以及后续标记/关联更新需要变化说明与理由。

### R-09 三态与覆盖

| 状态 | 定义 | 算覆盖 |
| --- | --- | --- |
| 空 | 没有标记 | 否 |
| 脏 | 有标记但过期，需要更新 | 否 |
| 已确认 | 已确认且没有过期 | 是 |

统计和列出受管内容的缺口，文本包括未覆盖的非空白范围。仅“已确认”算覆盖；不额外创造覆盖成熟度。判断何时过期及重叠状态聚合见 Q-01/Q-02/Q-08。

### R-10 分类、双向查询与实现方言

可以配置资源/对象类型：spec、其他文档、图、代码，以及 C、Python 等实现类别。同算法不同语言实现可以关联，支持反向查询。关系类型与方向属于工作流规则，不因双向查询就把语义方向抹掉。

### R-11 alias 与跨项目引用

由一个元数据目录组织关系，alias 在此目录定义。例如用户给出的来源标识是 `git:github.com/someprojectpath`，映射为 A 后使用 `proj:A:file_path`；当前/root 项目使用 `proj:root:file_path`。

该来源标识是设计示例，不能擅自补成别的 URL 或声称已验证远端。alias 到具体内容的解析、取得方式和版本选择仍是 Q-03，不从 `git:` 推导出核心依赖 Git。

### R-12 文本坐标与编码

文本位置按解码后的 Unicode 字符序号计数。默认编码 UTF-8，其他编码由用户显式指定；项目 TOML 或全局配置可设置默认编码。这里按码点而非显示宽度/字形簇理解；索引起点和端点边界见 Q-07。

### R-13 原始字节模式

`proj:A:byte::file_path` 表示原始字节偏移，可用于二进制或文本文件，不解码。不得与文本字符坐标混用。二进制的内容 hash/字节差异不承诺识别内部业务结构。

### R-14 固定 command 来源

格式为 `command::<executable>::<JSON args 数组>`，程序可为 bash、sh、cmd 或 powershell.exe 等直接运行的可执行程序。args 为硬编码 JSON 字符串数组。OMD 不提供动态参数、模板插值或命令编排。

### R-15 command 内容与成功条件

跟踪执行后的 stdout；必须正常退出且 exit code 为 0。stderr 不并入跟踪内容。失败产生的部分 stdout 不可作为成功的新基线，失败检查不能用旧结果冒充成功。空 stdout 且 exit 0 是合法空内容；exit 0 时 stderr 非空不单独构成失败。命令执行成功不等于标记自动确认。

## 工作流与写入

### R-16 规则型工作流

CLI 可设置确定性规则，例如：spec 上连 UML、下连代码；某目录代码必须关联另一个目录或项目中的对应实现。规则制定后不要求所有内容立即完成，可提醒或让指定流程检查失败。

### R-17 显式跳过

参照 pytest 测试用例的使用方式：手动指定参数跳过，或手动在配置中关闭检查用例。不加入自动豁免/审批/到期系统。跳过检查不改变标记三态。

### R-18 单写者与 hash 前置条件

禁止并发更新。更新须基于调用方先前读取的版本 hash；若当前 hash 不匹配，则拒绝并报错，不自动合并、覆盖或重新读取后悄悄强行提交。具体 hash 作用域、锁和中断恢复是 Q-09。

### R-19 人与 AI 同一契约

人类和 AI 使用同一 CLI、规则与写入约束，不设 agent 宽松通道。skills 指导 AI 执行工具流程，不替代核心确定性校验。

## 存储与发现

### R-20 权威数据与 SQLite

权威元数据采用可版本化的文本记录；SQLite 是可重建查询索引，不直接作为仓库内权威数据库。不因选择文本而依赖 Git。

### R-21 项目存储

默认项目根 `./.omd/`，支持用户指定任意其他元数据目录。用户配置可登记外置映射；两个路径按“项目根/元数据根”整理，具体字段仍是候选设计。

### R-22 配置与缓存路径

应用专用环境变量最高优先级：

```text
配置：OMD_CONFIG_PATH → Linux 的 $XDG_CONFIG_HOME/omd → ~/.config/omd
缓存：OMD_CACHE_PATH  → Linux 的 $XDG_CACHE_HOME/omd  → ~/.cache/omd
```

Windows/macOS 也先读这两个 OMD 变量，再采用平台原生目录。SQLite 不放项目元数据目录；其在缓存根下的隔离布局尚未冻结。

### R-23 单层发现

不使用默认 `.omd/` 时，可以在项目根直属子目录中识别特定 OMD 结构。不是全仓库递归查找。具体 manifest、根识别与优先级见 Q-10。

## 可选的 Lean 建模与程序性证明 skill

完整使用契约见 [programming-thinking.md](programming-thinking.md)。以下是后续补充的已确认要求，不是已经交付的 skill 或已经运行的证明。

### R-24 使用场景与排除范围

OMD 应提供 programming-thinking skill，用 Lean 分析已有 UML 细节中的顺序状态机、逻辑链及程序性遗漏，进行接近伪代码的预构建。必须先明确实际 UML 源码范围及待证明的正确性问题；不得泛化为任意文档的 Lean 转写。

本 skill 不用于并发、多线程任务的分析或证明，不以顺序模型冒充线程交错、锁或共享状态正确性证明。可隔离的纯顺序子过程只能声称其明确边界内的性质。这是本工作流的适用范围限制，不是 Lean 理论表达能力的结论。

### R-25 证明义务而非文档翻译

模型须显式表达输入域、状态、守卫、转移、数据变化、错误路径、前后置条件及假设，并针对声明的正确性问题给出实际通过 Lean 检查的命题与证明。应按目标检查分支覆盖/互斥、不变量保持、逻辑链衔接及终止等性质；未证明的性质不能顺带声称。

单纯类型检查、流程枚举、一次成功执行、自然语言回译或把结论当作前提不构成程序性证明。不得用占位证明、未证明自定义公理或空洞命题冒充完成；必须记录精确证明范围、假设与验证证据。

### R-26 预构建与实现严格对应

采用 Lean 程序性证明的范围，必须将经证明的预构建按程序语义单元严格一一对应地翻译为实际代码：状态、守卫、分支、转移、数据更新及错误返回不能遗漏或擅改。改变算法、控制流或相关语义时，先同步 UML/Lean 并重新证明，再更新实现。

一一对应不是把 proof tactic 逐行翻译为生产代码；类型表示、溢出、异常和外部副作用等影响性质的差异须显式处理。模型证明通过与人工/AI 翻译审查不能冒充跨语言实现已经端到端机器验证。

### R-27 Lean 必须直接关联 UML 和实际实现

用于程序性证明的 Lean 范围必须通过 OMD link 同时直接关联实际 UML 源码范围和实际实现代码范围，并保留理由及有效版本依据。关系必须细化到对应程序单元，不能只链接文件、标题、图片、伪代码或未来路径；经说明文档等其他节点的间接可达不能替代 Lean 与这两端的直接关系。

允许在实际实现产生前先完成模型证明，但必须报告实现及其 link 的缺口，不得声称闭环交付完成。任一必要关系缺失、过期或未复核都不满足闭环验收；证明所依赖的定义或版本变化也须重新核对。精确迁移、传播与规则 schema 仍由 Q-01/Q-02/Q-06/Q-09 细化，不增加第四种标记状态。

### R-28 可选工作流与诚实报告

Lean 是该可选 skill 使用的外部验证工具，不是 OMD 核心必需依赖。OMD 检查结构、内容版本与处理记录，不能因存在 link 就宣称语义正确。模型证明、实现对应审查、实现测试和关联检查须分别报告实际结果。

未使用此 skill 的项目不承担全项目 Lean 建模义务；采用后的范围须遵守 R-24～R-27。显式跳过检查仍符合 R-17，但不修复缺口或赋予“已证明交付”的资格。工具不可用或验证失败时如实说明，不编造通过结果。

- 将通用 programming-thinking 原样引入、把 Lean 当全局唯一事实源，或脱离 UML/实现仅转写文档，不采用；R-24～R-28 优先。
