## Goals / Non-Goals

**Goals:**

- 区分“通过实际修改接续传播”与“带理由阻断传播”，避免要求已经完成适配并提交的节点再补一次 clean。
- 保留源端对 1–n 下游分支的处置权，同时防止一个分支的 clean 抹掉另一个分支或其他变更的责任。
- 明确所确认的是哪个内容版本；目录身份、历史快照和当前观察不能混为一谈。
- 在形成实施规格前，用完整操作实例验证责任能否交接并最终清理。

**Non-Goals:**

- 本轮只整理规划并补齐 delta specs/tasks，不实现产品、不初始化 Rust/Lean 工程、不安装 hooks 或修改运行配置。
- 不引入第四种标记状态、自动豁免、自动语义判断或远端内容获取，不把本地项目 alias 固定为一个 Git 快照；显式 Git 内容来源另见 D-29。
- 不在本轮选择具体第三方库版本、许可证或发布方式；已审阅的记录、锁定、坐标和 CLI 契约仍须在实现中遵守，不能以选库为由改写。

## Decisions

### D-01：候选范围迁移后显式复核

**状态：已确认。追溯：R-08、R-09、R-12；Q-01；S-07、S-09、S-21。**

在已确认范围之前插入内容，所选正文没有变化而位置发生变化时，工具给出候选迁移，由使用者显式复核，不能自动迁移后沿用“已确认”。

用户明确允许固定英文理由，例如 `No substantive change.`。理由可由人或 AI 选用，但工具不能仅凭正文匹配自动声称没有实质修改。

选择该方案而非自动保持确认，是为了让迁移与语义判断的责任显式可见。Myers 提供匹配候选，不证明对象身份或语义等价。

**边界补充已确认：** 用户对紧贴末尾新增内容明确回答：“因为你无法确认新加的是否和老的相关，所以应该变脏”。因此，即使原范围的文字和起止位置均未变，恰好在末尾插入也使该范围变脏；不自动扩张范围或确认新增内容。开头插入造成原文位移，仍按既有规则复核；区间内部修改、跨边界修改也须复核。只有未受正文修改、位置迁移或边界插入影响的范围才能保留确认，不因文件 hash 改变而全部变脏。删除/拆分和重复匹配的明确处理入口采用已接受的 E-1。

### D-02：import 目录持续纳管

**状态：已确认。追溯：R-06、R-07、R-09；Q-04；S-03～S-05。**

**范围（用户明确）：** import/remove 的“纳管”仅指统计覆盖率与打 tag 的范围（见本节末尾的 tag 与 rule），不管理文件或 range；文件的跟踪始终靠用户对具体文件的显式 init/commit。因此本条的准确含义是：import 一个目录后，该目录范围进入覆盖率统计分母，后续检查发现范围内的新文件时将其呈现为空及覆盖缺口。不是仅登记 import 时的一次文件清单，也不需要后台监听才能成立；也不等于自动为文件建立跟踪。

未 import 不纳管、允许主动 import `.omd/`、follow 符号链接仍按原需求执行。纳入统计不等于自动确认新文件。

**已由后续决定解决：** 递归边界（全量递归，D-17）、显式排除（exclude/include，D-17）、重叠 import 的对象身份（import 不管理对象身份，D-17）、删除与复制（tombstone / copy 不自动关联，D-16）。文件初始化及重命名的迁移 commit 已由 D-15 补充。

**真正仍待明确的只有一条：** 迁移对已有范围、关联与确认有效性的影响——已由本节末的 D-19 确定。不能把文件重命名检测、自动接受迁移或自动保持确认作为本轮已定行为。reset 不改来源文件的既定边界不变，迁移后的旧路径与实际文件位置也不能靠 reset 静默覆盖。

### D-03：commit 接续传播，commit clean 显式阻断

**状态：已确认，以本轮纠正为准。追溯：R-08、R-09、R-16～R-19；Q-02、Q-08、Q-09、Q-11；S-06、S-07、S-18～S-20、S-22。**

用户明确纠正：“如果 b 适配 commit 了就说明手动 clean 已经被 commit 替代了”，并说明 clean 是 `commit clean --reason …` 子命令，“是阻断行为，而非断言说这里 clean 了，是指到这里为止了”。

| 操作 | 已确认含义 | 对传播责任的作用 |
| --- | --- | --- |
| OMD `commit --reason …` | 记录实际修改及原因；不是 Git commit | 若本次修改适配了指定上游变化，该提交接住该项影响；再处理本次修改对下游的影响，不需要返回上游补 clean |
| `commit clean --reason …` 或 `commit clean --no--reason` | 在当前节点显式阻断所选分支；可以提供理由，也可以明确选择不提供 | 表达“到这里为止”，不是对已完成修改再盖一次确认章；省略理由的例外见 D-10 |
| `commit unclean --reason …` | 显式引入脏状态，不要求内容发生变化 | 增加需处理的状态影响，不因内容 hash 相同被忽略；与回滚的区别见 D-09 |
| `reset <commit-id>` | 普通目标停在本身；ATOMIC begin/end 目标退到其前驱并警告 | 块内部目标拒绝；按实际落点撤下后续记录，不追加反向提交、不修改源文件，见 D-09、D-27 |
| `note` | 对指定 commit ID 添加外挂评论 | 每个 commit 对应一个平面评论数组，不改变该 commit 的传播效果或 ID，见 D-11 |
| `verify all cleaned` | 检查是否仍有未处理的变化/传播责任 | 不要求每个节点或每条关系都具有 clean 调用记录；实际适配提交与显式阻断均可推进完成 |

实际更新并提交，与不继续更新而显式阻断，是处理变化的不同路径。不能将任意不相关 commit 当作已经适配；也不能把必要修改未做且未显式阻断的分支静默当成已完成。阻断可按 D-10 显式省略理由，不意味着可以省略阻断操作。允许选择部分上游变化，见 D-08；具体 CLI 选择参数仍待规格化。

**撤销此前代理的错误推导：** “commit 永远不能代替 clean”“B 已适配并 commit 后，仍须回 A 执行 clean A→B”“每项必须额外 clean 才能通过”。这些不再是有效契约。用户强调不能省略 clean，是不能省略不继续向下修改时的显式阻断操作，而不是所有提交后都必须再 clean；理由可按 D-10 明确省略。

clean 不是第四种标记状态，也不是跳过检查。原有空、脏、已确认三态，以及 skip 不赋予确认资格的要求不变；覆盖如何由关系处理结果聚合仍需 Q-08 细化。普通适配/阻断不能绕过 broken 引用修复：引用悬空提交导致的 broken 属于脏状态，必须先 reset 到依据完整可达的提交，再重新 commit，见 D-14。

### D-04：逐节点接续，由源端选择阻断分支

**状态：已确认，完整实例见 D-07。追溯：R-08～R-10、R-16；Q-02、Q-08、Q-09。**

对 `A --> B --> C`，A 变化后处理 B 是否需要更新；B 实际适配并提交，接住 A 的相应影响，再处理 B 对 C 的影响。每次提交修改后，都可以在当前变更节点执行 `commit clean`，声明无需继续修改其下游；通常提供理由，也可按 D-10 显式省略理由。

- A 的变化无需 B 适配：在 A 端说明理由并阻断相应分支，不要求 B 替 A 解释。
- B 已适配 A 并 commit：不需要额外在 A 端 clean A 到 B。
- B 更新后无需 C 适配：在 B 端执行 `commit clean`，说明原因并阻断到 C。
- A 同时关联 B、C：允许只阻断 A 到 C，保留 A 到 B 的处理责任；也可以显式选择全部出向关联。

```text
    +--> B : adapt and commit
A --+
    +--x C : stop at A, with reason
```

选择源端分支操作，是为了符合一个变更源影响多个下游的模型；不采用目标端逐个替上游说明“不影响”的方式。

**直接约束：**

- 阻断仅对应本次变更及所选关联，不能自动沿用到该节点未来的新变更。
- 阻断 A 的某项影响，不能抹掉 B 自己的改动或其他来源带给 B 的责任。
- 处理 A 到 B 后，不能以推进全局确认依据的方式隐藏未处理的 A 到 C。
- B 适配 A 的提交，不会自动处理 B 的下游责任。
- 已确认的是逐节点处理、实际提交接续和源端阻断，不是“一次无条件将全部可达节点标脏”。

先前提出的“默认传播后收回”与“先裁决再传播”两个时序选项没有被用户选定。不能把其中任一内部时序作为已冻结决定；当前有效操作模型以上述最新澄清为准。

### D-05：verify/check 来源命令按配置默认值和本次参数执行

**状态：已确认。追溯：R-14、R-15、R-17～R-19；Q-05、Q-11；S-13～S-17、S-20、S-24。**

最初讨论只允许本次显式执行；用户随后补充并修订为：用户配置可以开启默认执行，本次参数可以覆盖。D-32 后续补充已明确 check 沿用同一开关与配置，不增设另一套许可。

```text
verify/check CLI flag > user config VERIFY_COMMAND_AUTO_RUN > built-in false
```

| 用户配置 | 本次 verify 或 check 参数 | 是否执行来源命令 |
| --- | --- | --- |
| 未配置或 `VERIFY_COMMAND_AUTO_RUN=false` | 无 | 否 |
| `VERIFY_COMMAND_AUTO_RUN=true` | 无 | 是 |
| 任意 | `--run-command` | 是 |
| 任意 | `--run-command=false` | 否 |

这里确认的是用户配置键与参数行为，没有额外批准同名环境变量或项目配置覆盖层。

- 未执行时，报告 command 当前内容未验证；不能将历史输出当作本次采集并声称当前内容全部验证通过。这是检查诊断，不是第四种标记状态。
- 正常退出且 exit code 为 0 时，完整 stdout 才能成为本次成功内容；stderr 独立诊断，空 stdout 合法。
- 采集输出未变且原处理依据仍有效时，不因重跑本身要求重新处理；输出改变后不能自动沿用旧提交或阻断结论。输出未变不能抵消另行执行 commit unclean 带来的待处理状态（D-09）。
- 启动失败、非零退出或异常终止时，本次验证失败，保留旧基线，不接受部分 stdout。
- clean 针对已采集的具体版本，不为确认再次运行来源命令。
- 开关控制 verify/check 对各自检查范围内来源命令的采集，不授权仅因读取配置或重建缓存就运行其中的来源命令。check 未采集或采集失败时，不得把旧输出的覆盖率冒充当前输出的覆盖率。

该选择同时保留默认不执行的边界与用户主动开启自动运行的便利；不采用“永远只能验证旧快照”或“每次都必须手动加许可参数”的限制。

### D-06：跨项目绑定本地目录，Git 标识只作可选身份校验

**状态：本地目录绑定与可选身份核对已确认；D-21 已取消 force。URL 比较等剩余行为见 Open Questions。追溯：R-04、R-06、R-11、R-18、R-20；Q-03、Q-09～Q-11；S-01、S-08、S-12。**

用户明确：“无论如何都只映射本地目录”，并且“跨项目关系一定是固定在目录这个概念，而非某个内容快照”。

- 用户显式关联两个本地目录，内容由用户自行准备；OMD 不负责下载、clone 或更新远端内容。这不是仅限首版的临时取舍。
- 项目 alias 绑定目录，跟踪目录中的当前内容；不提供将项目关联锁定在固定内容快照上的语义。
- 内容 hash、确认依据和必要旧内容属于 OMD 自己的变更/确认历史，不是 Git commit history，也不是项目目录关联的永久内容版本。
- 保留必要历史快照供 Myers 和复核使用，与“项目不固定在快照”并不矛盾；不能因此只存 hash 而丢掉基线。
- 可选的 `git:github.com/anything` 是帮助核对本地仓库身份的信息，不是远端获取指令。
- 配置了该信息后，每次命令运行都核对仓库实际 Git remote 是否仍对应登记身份；不只在首次关联时检查。
- 用户可在配置中显式登记身份对应关系，例如：

```text
git:github.com/anything --> git:git.example/any
```

- remote 不匹配时提示用户，不自动接受或静默修改绑定。**force 关联已由 D-21 取消**：用户通过显式更新登记（设置/修正别名）解决，不提供运行时 force 覆盖。

只关联目录而非固定快照，是为了持续跟踪演进中的项目。remote 检查是显式配置后的身份约束，不让无该配置的核心内容跟踪依赖 Git、Git 历史或联网。

**跨存储边界（用户补充确认）：** A、B 各自已有独立 `.omd/` 时，允许显式登记本地对方目录后直接建立跨目录引用；不要求先合并存储，也不隐式复制权威记录。读取和写入须核对参与方的版本与可用性。跨存储引用保护、单写者协调及查询范围在工程方案中一起细化，不能以缓存替代任一方的权威数据。

**尚需明确：** 登记中选择哪个 remote、URL 形式比较、身份核对不可用时的诊断以及 alias 修改操作。force 已取消，不再讨论一次性或永久旁路；是否支持跨独立元数据目录关联已不再待选。

### D-07：实际适配提交接住上游影响，不补重复 clean

**状态：按本轮用户纠正形成的行为实例；未执行产品测试。追溯：D-03、D-04；Q-02。**

以下只涉及给出的关联，假设不存在其他内容变化、缺失标记或检查失败。箭头表示影响处理方向，不代表最终关系类型名称；表中的分支选择说明不是已经冻结的 CLI 参数。

```text
A --> B --> D
|
+--> C
```

| 步骤 | 操作 | 尚未处理的传播责任 |
| --- | --- | --- |
| 1 | A 修改并执行 `commit --reason …` | A 对 B、C 的影响 |
| 2 | 在 A 端执行 `commit clean --reason …`，选定到 C 的分支，说明 C 无需适配 | A 对 B 的影响；到 C 在 A 处阻断 |
| 3 | B 为适配 A 而修改并执行 `commit --reason …` | B 对 D 的影响；B 的适配提交已接住 A，不需要回 A 补 clean |
| 4 | 在 B 端执行 `commit clean --reason …`，选定到 D 的分支，说明 D 无需适配 | 无；到 D 在 B 处阻断 |
| 5 | 执行全量清理验证 | 本例所列责任已经处理；其他检查同样满足时才能整体通过 |

若 D 确实需要适配，步骤 4 应改为实际修改 D 并提交，然后继续处理 D 的下游，而不是由 B 以 clean 声称“D 已经修改完成”。这两种操作分别表达接续与阻断，不能再要求两者依次发生才算完成。

实现必须能够辨别一次适配提交处理了哪些上游变化，以及一次阻断针对哪些出向分支，否则会误消除无关责任。部分上游选择已由 D-08 确认；具体选择参数、版本依据字段、聚合方式及持久布局尚未冻结，这不是已经批准的具体 schema。

### D-08：适配 commit 可显式选择部分上游变化

**状态：已确认。追溯：R-08、R-09、R-18；Q-02、Q-09、Q-11；D-03、D-04。**

A、X 同时影响 B 时，允许 B 的一次适配提交只处理明确选定的 A 变化，保留 X 的待处理影响。可选择一个、多个或全部上游变化；不要求全部上游都完成适配后才能提交。

```text
A --+
    +--> B --> C
X --+
```

| 操作 | 结果 |
| --- | --- |
| B 适配 A，并在 commit 中明确选择 A 的这次变化 | A 到 B 的对应影响已处理；X 到 B 仍待处理 |
| B 的本次修改影响 C | 接着处理这次 B 到 C 的影响 |
| 在 B 执行 commit clean，阻断这次变化到 C | 只处理该出向分支，不能消除 X 到 B 的未处理影响 |
| 执行 verify all cleaned | 只要 X 到 B 仍未处理，就不能因 A 分支已处理或 B 已阻断到 C 而通过 |

选择此方案是为了支持分步适配，并保留每项变化的责任；拒绝“任意 B 提交都清空 B 的全部上游影响”和“必须全部适配才能提交”两种行为。

**沿用已有版本约束：** 提交依据使用者先前读取的具体版本。所选上游内容或本次提交依据的相关内容/记录在写入前发生版本冲突时，按 R-18 拒绝，不改用新 hash 静默重试。command 以已采集的观察版本为依据，不为此重新运行。

**尚未由本决定解决：** 上游变化的标识与选择参数、expected hash 的精确粒度，以及多次未处理变化的展示/归并方式。不能仅凭理由文本猜测处理了哪些来源，也不能把来源选择等同于语义适配已经被核心证明。

### D-09：commit unclean 叠加脏状态，reset 移动有效历史位置

**状态：操作区别、普通 reset 目标本身保留及源文件不改已确认；ATOMIC 块内普通成员目标禁止，任意嵌套层级 begin/end 目标回退到直接前驱并警告（D-27）。悬空引用的 broken 判定及修复见 D-14；上层 reset 的范围恢复见 D-16/D-22，虚拟全局 root 不可 reset。追溯：R-08、R-09、R-18、R-20；Q-02、Q-09、Q-11。**

用户先明确状态操作区别：“revert 不是叠加是回滚，而 commit 可以直接 commit unclean 状态，这样无论有没有修改都必须处理脏状态，也就是所谓的层叠。”随后修订命名与语义：“revert 叫做 reset，逻辑跟 git 一模一样”。以最新修订为准。

- 支持显式 `commit unclean`：即使内容没有改变，也能引入必须处理的脏状态；理由要求沿用已有提交契约。
- unclean 是一次新的状态提交，不等于取消以前的提交，也不能只因当前内容 hash 与之前相同就当作无操作。
- 对合法普通目标执行 `reset c1`，有效状态移到 c1 本身，保留其效果，该作用域内 c1 之后的提交退出当前有效状态。ATOMIC 块内普通成员不能直接作为目标；任意嵌套层级 begin/end 目标按 D-27 移到其直接前驱，连目标标记本身一并撤下。虚拟全局 root 不可 reset；文件提交的范围恢复结果见 D-22。
- 历史记录保留与当前关联有效性分开：A reset 到 a0 后，a1 数据仍在但从当前有效根不可达；B 的 b1 仍引用 a1 时，verify 报 B 为 broken（脏），不自动改写引用或回退 B。修复由使用者将 B reset 到依据完整可达的提交后重新 commit，见 D-14。
- **普通目标的语义：** 不再称为 revert；普通 `reset c1` 不是“退回 c1 之前”。D-27 明确的 begin/end 特殊目标是例外，必须提示 warning；不能据此改变普通目标的行为。目标仍使用完整 commit ID 或唯一前缀（D-19）。
- 继续遵守此前明确选择的状态边界：只操作 OMD 的提交与跟踪状态，不恢复或改写用户源码、文档等来源内容，不运行来源命令补偿过去的副作用。
- 不追加反向 commit，不要求从末尾逐条撤销。reset 本身改变当前有效历史位置，不物理删除原 commit 及其外挂 note；记录未被另行清理时，仍可按原 ID 查看。退出有效历史与删除历史是两件事。
- reset 后仍检查真实来源内容。若磁盘内容与目标状态的基线不同，该差异仍须处理；移动历史位置不意味着当前内容自动干净。
- `commit clean` 仍表达源端阻断，不被本次补充改成完成盖章。unclean 也不增加第四种标记状态。
- 这是 OMD 自身的操作，不调用 Git 来保存或回退核心状态。Git 的目标提交语义不意味着在 OMD 中新增 Git index、分支系统、hard reset 或来源文件覆盖能力。

**一手资料校准：** [git-reset](https://git-scm.com/docs/git-reset) 的提交形式把 HEAD 指向目标 commit 本身；默认 mixed 与 soft 都不改工作树，hard 则会改。本项目已明确不改来源内容，不直接套用 hard 模式。[git-notes](https://git-scm.com/docs/git-notes) 将注释与被注释对象分开；[git-gc](https://git-scm.com/docs/git-gc) 说明不可达对象的清理另有保留与回收规则，不能把 reset 当成立即删除，也不能由此承诺永久保留。

**直接工程约束：** 内容版本与跟踪状态版本必须能区分。相同内容 hash 可以具有不同的未处理影响；显式 unclean、阻断和 reset 都会影响跟踪结果，不能把内容 hash 单独用作完整状态身份或索引有效性的依据。commit ID 的盐位于 hash 输入第一字段，具体元数据版本编码和 expected hash 粒度仍属 Q-09。

**尚未冻结：**

- 如何查找所有必要依据均可从根索引的回退目标的具体算法（可达性定义已由 D-16 给出）。D-14 的悬空引用判定已经确定，不得继续将其视为待决，也不能把派生的 broken 诊断等同于改写 B 的历史提交。
- 多次 unclean 的选择、合并展示方式。用户确认需要层叠，每个提交按 D-11 的随机盐/前驱/时间戳/本地内容公式生成独立 ID，但尚未冻结具体计数或存储模型。

**已由后续决定解决：** 退出当前有效历史的 commit、note 及必要基线的长期保留/清理策略——由 D-19 的显式 `omd gc` 命令解决。

### D-10：commit clean 可显式省略理由

**状态：已确认，修订此前理由必填要求的局部边界。追溯：R-08、R-18、R-19；Q-02、Q-09、Q-11；D-03、D-04。**

用户明确要求 `commit clean --no--reason` 可以不回答原因，例如前一个 commit 的理由只是对以前状态的补充说明和修订，不需要为了阻断再编造一段理由。

- 按用户给出的拼写记录 `--no--reason`；本轮不擅自更名为 `--no-reason`。
- 不选择该开关时，仍按既有 clean 契约提供理由；选择该开关时，可以不提供理由，仍产生有效的显式阻断操作。
- 工具需要区分“明确选择不提供理由”和“遗漏必填输入”，不能替用户伪造固定理由，或自动把上一条说明复制成新的阻断理由。
- 该开关只改变理由要求，不扩大所选分支、不跳过版本校验，也不改变 clean 的源端阻断语义。它不是 skip，不是自动识别“仅说明修订”的语义规则。
- 本次例外限于 `commit clean`；不据此把普通 commit 或 commit unclean 的理由默认改为可省略。

此前 R-08 和本次设计中无例外的“更新均需理由”表述，在此被用户明确细化；原 `docs/` 尚未同步，后续合并规格时应同步该例外，不能拿旧基线否定本轮决定。

### D-11：随机盐、前驱、时间戳与本地内容派生 commit ID；note 外挂

**状态：盐优先、完整提交输入原则，以及 project_id 仅作项目元数据而不进入 commit hash 已确认；具体字段 schema、前驱所属范围、字节编码和 reset 作用域仍需规范化。追溯：R-08、R-18～R-20；Q-02、Q-09、Q-11；D-03、D-09、D-10。**

用户核对 Git 对象身份后，明确选择“移出 hash，保留元数据”：`project_id` 继续用于项目登记和解析，不额外把项目归属绑定到提交 ID。该决定取代此前将 project_id 放在盐之后参与 hash 的方案。16 位随机盐仍是第一字段；本次提交的内容和完整不可变操作输入仍参与 SHA-256。区块链只作为前驱哈希 ID 的设计参考，不代表 OMD 采用区块链产品架构。

当前输入类别和顺序为：

```text
salt_16_chars = 16-character random string
previous_id = this node's previous commit ID, or "" if absent
timestamp = commit timestamp
content = local content under review
operation_payload = immutable operation inputs
commit_id = SHA256(salt_16_chars + previous_id + timestamp + content + operation_payload)
```

上述 `+` 表示按此字段顺序组成输入；盐是第一字段。`content` 覆盖本次提交涉及的本地内容，`operation_payload` 覆盖完整不可变操作输入，例如操作类型、理由状态/内容、选定上游 commit、来源/范围和 expected 版本。项目登记的归属信息不作为额外输入，也不通过 operation_payload 重新加入 project_id。note、缓存、当前派生状态和提交之后产生的数据同样排除。具体字段 schema、前驱所属范围以及 canonical 编码仍需规范化，不能把这段示意直接当作最终 schema。

- 盐固定在输入最开始；每次新 commit 生成新的 16 字符随机盐，不重新使用已有提交的盐和时间戳来冒充一次新提交。
- `project_id` 是权威元数据中的稳定逻辑项目身份，首次显式 import 或初始化时由 OMD 生成并持久化，不由本机路径、当前 Git remote 或目录内容自动推导。项目复制、路径变化或 remote 变化不自动改变它；显式身份迁移记录旧新身份关系，但不会重算已有 commit ID。
- 复制或引用已有提交时，保留其原始输入和 ID，不生成新盐、不把目标目录的项目身份注入旧记录。新发生的提交才生成新盐和时间戳。提交身份保持与项目登记归属是两个问题。
- 前驱是当前提交所属逻辑节点的上一条 commit，不是整个元数据目录最近的任意 commit，也不是所适配的其他节点的上游 commit。首条提交使用空字符串，不擅自替换为 null、全零 hash 或虚构父提交。“逻辑节点”的归属已由 D-16/D-17 确定为挂载树上的节点（文件节点、range commit 链、import 分支链等），不再是开放问题。
- 已确认 ID 绑定本次提交的完整内容和操作输入：盐、前驱、时间戳、本地内容和不可变操作元数据参与 SHA-256；项目登记信息不属于这些操作输入。具体字段 schema、字段顺序和 canonical 编码须由后续 schema 统一规定。
- 普通内容提交、`commit clean`（包括 `--no--reason`）、`commit unclean`，以及 D-15 的初始化/迁移 commit 应使用同一 ID 构成规则。即使本地内容相同，也不能把不同的状态提交合并成一条；每次新提交生成新的盐并检查已知 ID 是否冲突，碰撞时重新生成盐计算，不能覆盖旧记录。
- reset 不重写历史 ID；其后的新提交重新按最终公式计算，不复用已退出当前有效状态的旧提交 ID。reset 作用域已由 D-16 明确为“除虚拟全局 root 外任意 commit，级联到子节点”。
- 为使 ID 可复算，保留本次使用的盐、前驱、时间戳、内容依据和完整操作输入；复算时不重新取时间、随机盐或当前变化后的内容，也不查询当前项目身份来补充 hash 输入。具体持久布局仍属 Q-09。
- note、缓存、当前派生状态和提交之后产生的数据不属于原 commit ID 的输入；外挂 note 不改变原 commit ID。

**尚需设计的输入细节：** ED 清单仅提出了时间戳、盐字符集、ID 显示和存储格式等候选值，并未定义完整字段 schema、canonical 字节编码或事务格式。完整来源保存已按 D-22 确认；其记录布局仍须设计。不得将“未反对”或指向 ED 的链接当作上述细节已冻结。project_id 不重新引入 commit hash。

**参考与边界：** [Pro Git：Git 对象](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects) 描述按对象头与内容生成对象 ID，不包含额外的仓库身份；同一对象复制到其他仓库仍保持 ID。OMD 借鉴这种身份与存放位置分离，不照搬 Git 的 hash 算法、对象格式或整个架构。

**需与 D-09 联合核对：** project_id 的登记不自动决定逻辑节点、前驱范围或 reset 作用域。跨项目关系是传播/关联边，关联不等于合并提交历史。普通 reset 目标本身保留；ATOMIC 边界目标按 D-27 撤下标记并回退其前驱。两者都不修改来源文件。

`note` 是独立子命令，对指定 commit ID 添加评论。一个 commit 可以有多个 note，采用一维、有序的平面数组；不引入父评论、嵌套回复树或 PR 审批流程。

**note 的存储形态（用户明确）：** note 是单独的数据存储地方，只是一个对应 note 内容、note 时间和 commit ID 的记录。它可以对任意 commit 进行 note；任意 commit 也可以反查自己的 note list。note 不是 commit，不进入任何前驱链。

```text
commit c1 --> notes [n1, n2, n3]
commit c2 --> notes []
commit c3 --> notes [n4]
```

上图只表达关联形状，不是文件布局或最终字段定义；n1 等仅为示例标签，不是在此决定 note 的 ID 格式。

**外挂评论的直接约束：**

- 增加 note 不改被评论 commit 的 ID，不隐式改写其原始操作或理由，不自动执行 clean、unclean 或适配提交。评论可以补充/纠正说明，但不会仅因其文本就改变传播状态。
- 用户选择创建 clean commit，即使使用 `--no--reason`，仍然是有 ID 的状态操作；单独发一条 note 则只是评论。不能把两条路径混为一谈。
- note 是持久的用户信息，不能只存在于可删除的 SQLite 缓存；写入继续遵守单写者和旧版本冲突拒绝要求。

**后续工程结论：** E-2 不增加 note 作者字段；note 时间与持久追加顺序均保留。编辑/删除与长期保留已由 D-19 解决（只增不改不删，修改/删除作为新 note 叠加，gc 显式清理）。reset 本身不删除 commit 或 note，见 D-09。不额外添加回复树、评论解决状态、权限或通知系统。

### D-12：Git 样式状态数据库，区块链仅作 ID 生成参考

**状态：产品边界已确认；完整提交输入的具体字段 schema、逻辑节点身份、reset 作用域和持久化细节待定。追溯：R-01、R-04、R-08、R-18～R-20；Q-02、Q-09、Q-11。**

OMD 的目标是一个带提交、当前有效状态、关系传播、note 和 reset 的 **Git 样式状态数据库**。它不以 Git 为核心依赖，也不是 Git 的替代品；它管理的是文档—代码—图之间的关系处理状态。

区块链只提供 commit ID 的一个设计参考：使用前驱 commit ID、时间戳、盐和提交输入参与 SHA-256，使提交身份具备可追踪的前驱关系。这个参考不引入区块链的产品特性。

明确排除：

- 不引入不可验证篡改证明作为产品目标。
- 不因区块链类比引入 block/head 架构或额外标记生命周期；D-23 后续明确引入的 ATOMIC block 是多个 OMD commit 的原子操作分组，不是区块链区块。
- 不引入 PoW、挖矿、网络广播、节点共识、分布式账本或 Git index。
- 不把跨项目关联自动拼成一条全局提交链。
- 不从 ID 公式额外推导第四种状态、自动语义证明或历史不可删除承诺。

提交状态、传播关系、note、来源快照和当前有效记录仍按 OMD 自己的权威文本与可重建索引模型设计。`project_id` 保留为项目登记和解析元数据，不进入 commit ID；它不决定全部关系传播，也不替代 alias、来源、范围或版本记录。

**尚需核对：** 各节点的前驱链、完整来源依据与当前有效记录需要独立表达；ED 候选未定义完整 schema/canonical 编码/事务恢复协议。文件 reset 恢复目标提交时的范围版本，见 D-22；恢复结果已确定，存储方式尚未选择。不能因为 ID 参考区块链，就自动引入区块链的数据结构或产品功能。

### D-13：未来产品 skill 提供 worktree 目录组织方案

**状态：后续附带 skill 的任务已确认；不是新增核心能力或本轮 skill 实现。追溯：R-01、R-03、R-04、R-11、R-19、R-21；Q-12。**

用户要求把 Git worktree 作为未来 OMD 随附 skill 提供给 AI 的现成使用方案：引导用户舒适地组织外置 OMD 元数据仓库、多仓库本地 link 和对应工作目录，避免 AI 或用户重新发现/发明已有方案。

用户给出的具体组合是：一组工作区放 A 项目的 B 分支、OMD 元数据仓库的对应分支、可选 C 项目的 A 分支；另一组放 A 项目的 main 分支与其余仓库的对应分支。不同仓库的分支名不需要相同，“对应”由用户选择，不由工具根据名称猜测。

以下仅是未来 skill 的目录示意，不是已创建目录或可执行配置：

```text
workspaces/
+-- feature-b/
|   +-- project-a/  [repo A, branch B]
|   +-- omd-data/   [repo OMD, matching branch]
|   +-- project-c/  [repo C, branch A; optional]
+-- main/
    +-- project-a/  [repo A, branch main]
    +-- omd-data/   [repo OMD, matching branch]
    +-- project-c/  [repo C, matching branch; optional]
```

父目录提供组合工作区；每个子目录分别属于自己的 Git 仓库，可以是该仓库的 linked worktree。不是让一个 worktree 同时属于 A、OMD、C 三个仓库，也不是通过父目录创建新的统一仓库。

- skill 在用户采用 Git、确实需要多个工作目录时推荐该方案，并提供经过验证的目录布局、外置元数据位置和本地 alias 配置示例；不强制迁移用户已有布局。每组使用自己配对的 OMD 元数据目录与来源目录，避免映射误指向另一组的同名项目。
- C 是可选成员；只有 A 与外置 OMD 元数据仓库也可组成工作区，不要求为了示例补造第三个项目。
- 组合类似 workspace 的目录体验，但不是 Cargo workspace 那样由工具原生统一管理的成员集合。Git worktree 不提供跨仓库原子的 checkout、commit、reset、merge 或 push；一组目录也不代表三份仓库内容已经语义同步。指南不承诺自动配对、同步分支或新增工作区编排器。
- worktree 是外围目录组织工具，不成为 OMD 的来源、项目身份、差异、基线、版本或锁实现依赖。普通目录使用不变。
- [Git 官方 worktree 文档](https://git-scm.com/docs/git-worktree) 明确 linked worktree 属于同一个 Git 仓库，不会把多个独立仓库自动合并成一个工作台。指南应说明：不同仓库各自准备 worktree，再通过父目录布局和 OMD 显式本地关联组合起来。
- 外置 OMD 元数据仓库也可使用自己的 worktree。Git 的工作目录隔离不等于 OMD 并发写入许可；多个调用若指向同一元数据根，仍遵守单写者约束。
- 目录移动、worktree 移除与 alias 路径维护需要在后续指南中交代，不承诺 Git 自动修复 OMD 的本地映射。不把 Git refs 的共享或默认同分支检出限制隐藏起来，也不默认建议 force 绕过。

本轮只记录附带任务，不创建/安装产品 skill，不执行 git worktree、分支或仓库创建命令，不新增 OMD 自动编排 worktree 的功能。具体指南和示例在产品 CLI/映射契约明确后单独编写与验证。

### D-14：悬空引用导致 broken，reset 后重建；支持悬空提交管理

**状态：判定、修复路径、诊断术语与功能目标已确认；根索引规则、重放与清理细节待定。追溯：R-09、R-18、R-20；Q-02、Q-09、Q-11；D-03、D-09、D-11。**

用户明确：A reset 到 a0 后，不直接删除 a1。B 的 b1 指向从根树搜索不到的悬空 a1，verify 应警告 B 的状态是 broken，且 broken 是脏状态的一种。修复只能先 reset 到如 b0 这样所有必要信息均可从根索引的提交，再重新 commit。还需提供查找磁盘上仍存在但已悬空的 commit，以便查看、重放或清理其数据。

**诊断术语（用户明确）：** 悬空本身叫做 **dangling**（悬置）；因 dangling 关系而 broken、需要修复的状态叫做 **unreachable_link**（断链）。unreachable_link 与 dangling 都是 dirty 的诊断原因，不是第四种标记生命周期。

#### 判定与修复

- **磁盘存在不等于当前有效可达。** a1 即使仍能按 ID 读取，也可能已退出当前有效根所索引的历史。b1 对 a1 的引用不能仅凭“还能读到数据”就使该适配有效，也不能反过来把 a1 自动纳回有效历史。
- **broken 是脏状态的诊断原因。** 对受影响的 B 报告 broken 及其悬空引用，不新增第四种标记生命周期。有未修复的 broken 时不能声称 `verify all cleaned` 已通过；显式跳过检查也不修复它。
- **必要依据的间接断裂同样导致 broken。** 用户补充确认：若 c1 依赖 b1，b1 本身仍可索引，但其所依赖的 a1 已悬空，则 verify 此时也报告 C 为 broken，不必等 B reset。诊断展示如 `c1 --> b1 --> a1 (dangling)` 的原因路径。这是引用依据完整性检查，不改变 D-04 普通内容变化逐节点处理的规则，也不自动回退或改写 B、C。
- **必须先回退到完整可用的依据。** 为 B 选择如 b0 的提交，其直接和间接必要依据均完整可用、可从当前有效根索引，然后 reset B，再基于当前有效依据重建提交。候选回退目标也不能仅凭直接引用可找到就判定可用。不能在 broken 的 b1 上追加普通 commit、commit clean（包括无理由模式）、commit unclean 或 note 来跳过这个修复步骤。
- **不改写旧记录。** 不把旧 b1 中的 a1 静默替换为 a0，不因 b1 broken 自动删除它或其评论。重建是新的提交，按现有盐/时间戳/前驱规则生成新 ID，不能冒用原 b1 ID。
- **诊断提供可执行的修复线索。** 指明受影响节点、当前 unreachable_link commit ID、dangling 目标 ID，以及经过检查的可回退 commit ID；例如说明需 reset 到 b0 再重新 commit。找不到合格目标时如实报告，不能编造 b0 或推荐同样含悬空依据的记录。精确 CLI 参数另行规格化。
- reset 仍不修改来源文件。来源实际内容与恢复后的基线是否匹配，由已有内容检查规则单独判断；引用完整并不自动证明内容或语义正确。

**项目根与挂载树（用户补充确认）：** 同一项目中的 A、B 等文件节点都指向一个项目根；这个根只用于挂载这些文件节点。这是项目结构可以构成树的前提。这里描述的是 OMD 的逻辑挂载关系，不是要求磁盘目录改成某种布局。

挂载关系与适配/必要依据引用须区分。b1 引用 a1 只提供依据关系，不能把已退出有效历史的 a1 重新纳入挂载树。按 D-17，项目根下的 import 与文件是平行分支，文件下挂 range，import 不是文件的祖先。文件 commit 回退同时恢复其目标提交时的 range 版本（D-22），不以关联边代替挂载关系。文件 init 只登记文件自身，不与上游适配合并；range 之间的依赖不能写成文件 init 的依赖。

#### 悬空提交管理

- 提供列出指定 OMD 存储检查范围内所有“磁盘仍存在、但从当前有效根不可达”的 commit 的功能，不只列出本次 reset 刚撤下的记录。CLI 入口已由 D-17 确定为 `omd list --dangling`。
- 支持按 ID 查阅这些提交的数据；查看本身不使其重新有效，不创建新提交，也不触发来源 command。
- 支持用户显式查看或清理悬空提交。**重放的含义（用户明确）：** 所谓“重放”不是 OMD 的自动操作，而是用户用 CLI 命令打开该 commit 查看信息，然后自己手工在别的地方重新应用。OMD 不提供“一键重放为新提交”或“恢复旧提交有效性”的命令。清理策略已由 D-19 确定为显式 gc 命令，由用户主动触发。
- reset 与 verify 不自动执行重放或清理。不能因为诊断指出 a1 悬空，就擅自恢复 a1 以掩盖 B 的 broken，或立即删除 a1。批量清理应有明确目标和写入前的版本校验，不能让其他有效数据丢失。

### D-15：初始化与文件路径迁移 commit

**状态：初始化/迁移 commit 及其 path.source、path.target 含义已确认；初始化只登记文件自身，不与上游适配合并。迁移执行与关联处理细节待定。追溯：R-06、R-08、R-09、R-18、R-20；Q-04、Q-09、Q-11；D-11、D-14。**

用户明确：文件重命名如 B 到 C、随后 A 到 B，应记录为迁移 commit；迁移的 path 中有 source 和 target。文件节点的第一条 B0 是初始化 commit，没有 source，或省略 source，只有 target。文件节点挂载于项目根，根的职责见 D-14。

以下只展示 path 字段，不是完整提交 schema 或可执行命令：

```text
B0 initialization: path = { target: "B" }
B-to-C migration:  path = { source: "B", target: "C" }
A-to-B migration:  path = { source: "A", target: "B" }
```

- 初始化的 path.source 省略，path.target 指向初始路径；不能用项目根路径冒充迁移 source。迁移的 path.source 是迁移前路径，path.target 是迁移后路径。
- **由示例直接推出：** B 到 C 后，A 可以迁移到已经腾出的 B。此时路径 B 对应原 A 的迁移结果，原 B 已迁到 C；不能因路径字符串再次为 B，就把原 B 的提交、note 或关联悄悄接到原 A 上。具体节点标识格式仍未选定。
- **沿用 D-11：** 初始化/迁移都是有 ID 的 commit；操作类型与实际 path 输入属于不可变操作输入，参与 commit hash。首条初始化 commit 的 previous_id 按既有规则为 `""`，它与省略 path.source 是不同字段。项目根的挂载关系不因此变成一个虚构的前驱 commit。
- **术语边界：** path.source/target 表示文件位置；previous_id 表示提交前驱；上游适配依据是另一类引用。只有 target 的路径记录，不足以决定初始化 commit 是否同时允许记录上游适配依据。初始化也不自动赋予内容“已确认”或覆盖资格。
- **初始化与适配分开（用户明确确认）：** B0 初始化只登记该文件节点的初始化，不能同时记录“已经适配上游 a1”；上游适配只能在初始化之后的适配 commit 中记录。这样 a1 悬空时，B0 自身不因一项上游适配依赖而 broken；初始化中的该文件能否成为合法回退目标，仍须检查其内容与后续迁移/其他必要依据是否完整。

**初始化时机（用户确认）：** 用户明确“import 是 import 文件夹的 commit，init 是 commit 文件的 commit”，并确认推论：init commit 由用户对文件的显式 commit 动作产生，import 不批量生成 init。未 init 的文件在 check 的内容覆盖统计中呈现为未标记缺口，不因这项覆盖不足使 verify 失败（D-02、D-32）。

**仍待明确：** 迁移对已有范围、关联与确认有效性的影响——已由 D-19 确定（迁移后保持确认与关联，仅 path 变化）。

### D-16：虚拟全局 root、手动 rename commit、verify 存在性确认、copy 不自动关联、tombstone 删除

**状态：虚拟全局 root、手动 rename commit、verify 存在性确认、copy 不自动关联、tombstone 删除均已确认。追溯：R-06、R-09、R-18、R-20；Q-04、Q-09、Q-11；D-09、D-14、D-15。**

用户明确：

- **虚拟全局 root（唯一根）：** 项目根再往上还能绑定一个虚拟全局 root，用于关联所有本 OMD 关联的项目（如 git 仓库）。file path 的稳定基座是虚拟全局 root → 项目根 → 文件节点。项目根的加入通过 **add project commit** 记录。
- **commit 的层级对象（用户明确）：** import commit 是 import 文件夹的 commit；init commit 是 commit 文件的 commit。两者分别作用于目录层级和文件层级，不是同一个 commit 的两个阶段。
- **手动 rename commit：** 迁移 commit 由用户手动 commit 产生，不是 verify 自动检测。verify 只确认最新的所有 commit 所指向的文件是否真实存在于磁盘上（逐个算 hash 确认）；它不主动发现改名、不自动登记迁移。
- **copy 不自动关联：** 复制产生新节点，目标路径走初始化 commit；不自动记录来源、不自动建立传播关系。如需跟踪，另行显式 link。
- **统计与跟踪分离：** 不在 import 范围内的文件不进入该范围的覆盖统计。import/remove 不建立或删除已显式 init 的文件/range；不能据此跳过已经跟踪的对象。
- **tombstone 删除：** 删除是一种 commit：节点有效状态记为已删除，历史和 note 保留可查；仍引用它的依赖方报 broken。磁盘上文件消失但没有 tombstone 时，verify 报节点缺失（脏），区分有意删除与文件丢失。

#### 层级模型

```text
virtual_global_root (唯一根)
  +-- project_root A (add project commit)
  |     +-- file node B: B0(init) --> B1 --> ...
  |     +-- file node C: C0(init) --> C1 --> ...
  +-- project_root X (add project commit)
        +-- file node Y: Y0(init) --> Y1 --> ...

add project commit: 将 project_root 挂到 virtual_global_root 下
import commit:      文件夹层级的范围 commit（全量，仅用于统计覆盖与打 tag），可由后续 exclude/include commit 层叠修改；不管理文件或 range
file init commit:   文件层级的初始化 commit（只有 path.target）
range node:         文件节点下的字符/字节 range 跟踪节点，是真正会变脏的对象
command object:     与文件节点平行的虚拟文件对象，由 commit 初始化，比对的是运行输出而非磁盘 hash
```

**每个 commit 都记录时间（用户明确）：** 无论哪一层、哪一种 commit，都必须记录提交时间。这与 D-11 中 timestamp 参与 hash 一致。

#### 树的第四层：range 节点与文件 commit 的职责（用户明确）

树不止到文件层面，而是到字符 range 层面：一个文件的 init commit 节点下再出现很多字符/bytes 跟踪节点。**这些 range 节点才是会变脏的对象；文件节点 commit 本身不会变脏。**

文件 commit 节点存在的意义是跟踪 hash 值的变化：

1. 文件 hash 变化后，verify 用 Myers 算法（即 git diff 的算法）检查该文件节点下哪些 range 节点受影响，**只有算法指出的受影响 range 才标记为脏**，未受影响的 range 保持已确认。
2. 用户逐个解决脏 range 并 commit。
3. 当该文件下所有脏 range 都解决后，用户运行 `commit verify <文件路径>`（参数形式类似 git add）。若 verify 通过，产生一个 **hash 变化的 commit**，记录该文件最新的 hash。

```text
file node B: B0(init, hash=h0) --> B1(hash changed, hash=h1) --> ...
  +-- range r1: r1.0(confirmed -> dirty, Myers hit) --> r1.1(confirmed, user commit)
  +-- range r2: r2.0(confirmed)   [Myers 未命中，保持已确认]
  +-- range r3: r3.0(confirmed -> dirty, Myers hit) --> r3.1(confirmed, user commit)
→ r1/r3 都解决后，`commit verify B` 通过，产生 B1(hash=h1)
```

这与 D-01 “候选迁移+显式复核”兼容：Myers 给出哪些 range 受影响，用户逐个复核；不因文件 hash 变化就把全部 range 标脏。

#### command object（用户明确）

注册的 command 与文件共用同一套跟踪逻辑，区别只在取得内容的方式：文件读完整文件内容，command 取得已登记命令正常成功退出的完整 stdout。内容取得后照常计算 hash、保存完整来源版本，并由 verify 的 Myers 差异定位受影响 range；不为 command 另建标记状态、版本体系或提交路线。

verify/check 中是否执行按 D-05 的同一配置/参数决定；首次初始化采集及工作目录见 D-28。未执行或采集失败时，不冒充已经取得新的成功内容，不消除原有待处理责任，也不声称当前内容已验证。

按 D-17，import 分支与文件式来源对象分支平行挂在 project root 下，range 挂在相应对象下。后续 D-28/D-29 增加的来源方式不新增挂载层级；该层级不依赖磁盘目录层数。

挂载关系与提交的适配/必要依据引用须区分。真实文件的 verify 读取当前登记路径上的文件；已记录的旧内容按其保存方式取回，可能来自文件副本，也可能来自确切的 Git 版本。历史 Git 内容可读不能掩盖当前路径缺失，当前文件存在也不能替代丢失的历史对象。虚拟 command 的当前内容仍按执行许可采集完整 stdout。来源检查不沿适配引用恢复悬空记录，也不把 dangling 记录重新算作有效（D-31）。

#### rename commit 的手动流程

1. 用户在磁盘上把 B 改名为 C。
2. 用户显式执行 rename commit，记录 `path = { source: "B", target: "C" }` 和 reason。
3. verify 检查最新 commit（C 的 rename commit）指向的 C 是否在磁盘上存在且 hash 匹配。
4. 若用户未登记 rename 而直接改了磁盘，verify 发现最新 commit 指向的 B 不存在，报告 missing；若 C 位于有效 import 的应计范围内，check 将其未标记内容计作覆盖缺口。系统不自动认定 C 就是原 B。用户需显式登记正确的 rename commit 才能恢复对应路径跟踪。

#### copy 与 delete 的行为

- **copy：** B 复制出 C 时，C 走自己的 B0 初始化 commit（`path = { target: "C" }`），与原 B 无自动关联。原 B 的历史、note、链接不受影响。
- **delete：** 删除通过 tombstone commit 记录。用户明确：tombstone 本质是迁移 commit 的一种——`path.source` 为原路径，`path.target` 指向 null。它不是独立的 commit 类型。节点的有效状态变为「已删除」，历史和 note 保留可查。仍引用该节点的依赖方报 broken（具体诊断名后续归类）。磁盘上文件消失但没有 tombstone 时，verify 报节点缺失（脏），与 dangling 区分：dangling 是记录仍在但退出有效历史；缺失是磁盘文件不在。

```text
B0 initialization:  path = { target: "B" }
B-to-C migration:   path = { source: "B", target: "C" }
C tombstone:        path = { source: "C", target: null }
```

由此直接推出：tombstone 后同路径再出现文件，走新的初始化 commit（`path = { target: "C" }`），是新节点；旧链以 `target: null` 终结，不与新链自动接续。

#### reset 的作用范围（用户明确）

reset 可作用于不同层级的提交，虚拟全局 root 不可 reset；后续 D-23/D-27 又明确 ATOMIC 块内普通成员目标禁止、任意嵌套层级 begin/end 目标回退到直接前驱并警告。普通目标仍保留本身，其后记录成为 dangling。不修改磁盘、不物理删除记录的约束不变。

**文件与范围的回退：** range 自身 reset 到合法普通目标时，保留目标范围 commit 并恢复其状态；ATOMIC 特殊目标按 D-27 处理。用户另已明确确认：reset 文件提交 B2 到 B1 时，其下范围也恢复到 B1 当时的版本；不是一律清空范围，也不要求再单独 reset 每个 range（D-22）。保留目标，后续被撤下的提交成为 dangling，记录与 note 不被 reset 删除，磁盘文件不动。该行为不指定必须复制整棵树或采用事件重放。挂载路径分为 `root -> project -> file/command -> range` 和 `root -> project -> import` 两支；import 不拥有平行的文件/range 分支。必要依据引用用于诊断，不使已 dangling 的记录重新有效。

#### import 的范围与层叠（用户明确）

import commit 是全量将该文件夹（含子目录）计入覆盖率统计范围。之后用户可用 **exclude commit** 和 **include commit** 层叠调整范围，逻辑是层叠：后的 commit 覆盖前的同范围判定。不添加隐式排除；`.omd/` 仍可显式 import。

**语法（用户明确，先定下来，不当默认）：** `--exclude <pattern> --exclude <pattern> --include <pattern>` 可多次传参；写法与逻辑参考 `.gitignore`（相对 import 根的模式匹配，后写规则覆盖先写规则）。

```text
import  dir/           -> 全量纳管 dir/ 及子目录
exclude dir/build/     -> dir/build/ 不再纳管
include dir/build/keep -> dir/build/keep 重新纳管（覆盖上一条 exclude 对该路径的判定）
```

exclude/include 的匹配语法已由 D-17 确定为 `.gitignore` 式（相对 import 根的模式匹配，后写覆盖先写）。

**以下三项代理候选值已由主人确认：**

- 诊断名：`missing`（磁盘文件不在且无 tombstone）/ `dangling`（记录在但退出有效历史）/ `unreachable_link` / `conflict`，与 ED-16 的 `diagnostics.kind` 一致。
- 虚拟根持久化：作为 `.omd/` 中一个特殊的 commit 文件（如固定 ID 的 `root.toml`），唯一性靠单写者锁 + 首次 init 时创建保证。
- tag 命名冲突：tag 是项目内平面字符串，同名即同一个 tag（这是特性，新文件打同名 tag 自动受约束）；跨项目不共享，跨项目规则需显式引用对方项目的 tag。

exclude/include 语法与 rule 失败级别已由本节确定。

### D-18：查询命令——`omd log`、`omd tree`、全局 `--json`

**状态：用户明确。追溯：R-18；Q-11；D-11、D-14、D-16、D-17；ED-16。**

用户明确：

- **`omd log <commit-id>`：** 类似 `git log`，沿 previous_id 链展示该 commit 的历史（commit ID、时间、操作、理由）。记录在的 commit 都可以查看，包括 dangling 和 tombstone 的 commit——这也是 D-17“重放 = 打开看信息后手工重做”的查看入口。
- **`omd tree [<commit-id>] [--level ...]`：** 类似 bash 的 `tree` 命令，显示挂载树的层级关系。不给 commit-id 时缺省从虚拟全局 root 开始；给出 commit-id（如某文件 commit）则从该节点开始。可限制层级，例如只到 project 或只到 file；不限制时一直显示到 range。
- **全局 `--json`（用户确认）：** 所有命令都可以 `--json` 输出 JSON，tree 尤其如此，以便与脚本集成。沿用 ED-16 的统一 envelope。

```text
omd tree --level file

root
├── proj/A
│   ├── [import] import -> exclude -> include
│   └── src/main.rs  (B0..B3)
└── proj/X
    └── docs/spec.md (Y0..Y1)
```

**边界：** tree 显示的是挂载层级（虚拟根 → 项目根 → import 分支/文件节点 → range），不是 link 引用关系；两者是不同遍历域（D-14）。

**工程候选默认（实现时可修订）：** 裸 `omd log`（无 commit-id）按时间倒序列出最近的 commit。

### D-19：迁移后范围保持、note 修订链、显式 gc、reset 目标语法

**状态：迁移后范围保持确认、note 修订链、显式 gc、reset 目标语法均已确认。追溯：R-06、R-08、R-09、R-18；Q-02、Q-09；D-09、D-11、D-14、D-15、D-16、D-17。**

用户明确：

- **迁移（rename）后原节点上的已确认 range commit 保持确认，link 关系不变，只是 path 从 source 变 target。** diff 是 verify 的时候跑的，commit 就只是 commit，这俩没关系。迁移不产生重新 diff，也不改变任何 commit 的内容或标记。
- **note 只增不改不删。** 每个 note 有自己的 note id。修改和删除不是原地操作，而是特殊的“delete note”或“patch note”——即在同一个 note id 上追加一个新 note。修改就是一个 patch 加到 note id 上的一个新 note。原始 note 保留，修订历史可追溯。
- **dangling commit 的长期保留策略：显式 gc 命令。** 由用户主动触发清理，不自动到期。具体命令名、清理范围与保护规则尚未冻结。
- **reset 目标语法：仅完整 commit ID（或唯一前缀），不提供 `HEAD~1` 之类的父提交简写。** OMD 的链模型简单，直接用 ID 最明确。

### D-21：unclean 展示、gc 保护规则、force 取消

**状态：unclean 平面展示、gc 保护规则及取消 force 已确认。追溯：R-08、R-18；Q-05、Q-06；D-06、D-09、D-14、D-19。**

- **多次 unclean 的展示：平面列出全部。** 每条 unclean commit 独立存储独立列出，按时间序平面展示，全部须处理。与 note 的平面数组一致，不做合并计数。
- **gc 保护规则：不可达且无引用才清理。** 一个 commit 被 gc 清理的充要条件是：从虚拟根不可达，且没有任何有效 commit 引用它。被引用的 dangling 保留（诊断仍可读）。commit 被清理时其 note 一并清理。具体命令名仍为工程默认。

### D-20：多用户冲突不提供解决工具；commit 支持显式时间戳参数

**状态：用户明确。追溯：R-18、R-20；D-11、D-14、D-17、D-19；ED-09。**

用户明确：

- **多用户冲突场景：** 如果两个用户在同一个 OMD 工作，可能产生冲突（各自写入了不同的后继 commit）。
- **OMD 不提供冲突解决工具：** 不做自动合并、不提供 mergetool、不比较两条分歧链的优劣。
- **commit 增加显式时间戳参数：** commit 支持 `--时间戳` 类参数（CLI 形式实现时定，如 `--timestamp`），用户可显式指定该 commit 的时间戳。指定值照常参与 hash（D-11 公式中的 timestamp 字段），确定性不变。
- **用途是手动重放解决冲突：** 用户查看对方历史（`omd log`）后，用指定时间戳在本地重建相应的 commit 序列，形成自己想要的历史顺序。这与 D-17 “重放 = 查看后手工重做”一致，`--时间戳` 是手工重放的必要工具。

**边界：** 时间戳参数不改变单写者锁（ED-09 仍防同机并发写），不改变“expected hash 冲突拒绝、不自动合并”（R-18）。时间戳的真实性由用户负责，OMD 不验证它是否接近真实时间；冲突谁对谁错由用户判断。

### D-17：link 只连接 range；commit 子命令别名体系；脏状态按 commit 而非位置判定

**状态：用户明确。追溯：R-08、R-09、R-11、R-18、R-20；Q-01、Q-02、Q-04、Q-07、Q-08、Q-11；D-01、D-03、D-11、D-14、D-16。**

#### range commit 的新建与续改

用户明确：range 节点（文件下的字符/字节跟踪节点）直接由 `commit --range` 初始化：

- **无 `--id`：** `commit --range <范围>` 新建一个 range commit，即新跟踪节点的首个 commit。range commit 可以相互重叠；**完全相同的 range 也可以打多个并行的 commit**（各自独立成链）。
- **有 `--id`：** `commit --id '<range commit id>' --range <范围>` 在该既有 commit 的基础上 commit；`--range` 此时意味着修改该跟踪的范围。

由此直接推出：range 跟踪节点的身份不是坐标本身（坐标可重复、可并行、可修改），而是**从首个 range commit 开始的 commit 链**；节点标识经由 commit ID 链确定。

#### link 的对象是 range

用户已在 D-24 明确纠正：link 连接的是 range 跟踪对象，不是两个孤立的 commit 版本节点。**不可以直接 link 一个文件到另一个文件。** link 仍是 commit 下的子命令；某次操作、版本依据和关联实例的身份分别记录。此前将两端写为 range commit 并据此推导“每个新版本要建立新关联”的解释撤回。

D-03/D-04/D-07/D-08 中的“A → B”连接范围跟踪对象，具体关联实例按 D-24 的 link ID 区分；文件节点之间没有直接传播边。D-14 中“b1 引用 a1”表达某次记录的必要版本依据，不是把 link 的端点定义为 a1/b1 两个版本节点。早先示例用文件名代指对象的地方，也不能据此引入文件级 link。

#### 脏状态按 commit 而非按位置判定

用户纠正代理候选默认“同一位置同时有脏和已确认 range 时该位置算脏”：脏不是按位置，而是**按 commit 的 range 来确认**。如果 diff 确认某一行是变动，那么覆盖该行的相关 commit 都会变脏。用户可以用 `commit clean --no--reason` 取消脏状态（D-10），并用截断传递（D-03/D-04 的源端阻断）去阻止脏状态传播。不引入“位置级”的合并规则。

#### 没有 Myers 基线存储这个概念

Myers 是 verify 时计算差异的算法，不另设名为“Myers 基线”的独立存储体系。

**完整来源版本（本轮用户确认，git 来源例外见 D-29）：** 文件与 command 的提交记录保留对应完整文件或完整命令输出，range 引用该来源版本与坐标。verify 对所有来源都比较完整旧新内容，再判断哪些 range commit 受影响；file/command 的旧内容须能从 OMD 权威记录恢复，git 来源则按 D-29 从指定仓库对象取得。SQLite 不作为任何一种来源唯一的必要依据存储。

这取代此前“仅将 range 片段与当前完整文件比较”的代理推论。例如同一文件有两段相同的 `abc`，只跟踪第二段时，旧完整来源及原坐标提供定位依据；仍不得将差异匹配当作语义等价证明。

#### commit 子命令别名体系

用户明确：import / remove / delete / init 都是 commit 的别名：

```text
import <dir>   == commit import <dir>    文件夹层级计入覆盖率统计范围（全量，见 D-16 tag）
remove <dir>   == commit remove <dir>    退出该文件夹的覆盖率统计整体；不删除已在跟踪的文件/range，历史保留
init <file>    == commit init <file>     文件层级初始化（D-15 的 B0）
delete <file>  == commit delete <file>   对应 init，即 tombstone（D-16 的 target: null）
link           == commit link            range 之间建立有 link ID 的定向关联
clean / unclean / verify                 已在 D-03/D-09/D-16 定义
```

remove 与 exclude 的关系（用户明确）：remove 退出的是**检查百分比的整体**——它不会删除已经在跟踪的文件或 range，历史保留可查；exclude 只是在 import 范围内层叠排除子路径。import 和 remove 只为统计百分比和打 tag（见下）服务，没有别的用途，不直接管理文件或 range。

#### tag 与 rule（用户明确，Q-06 的解答）

规则是**命名的检查集合**。用户可以在 import 的时候或之后用 `commit tag` 的方式给某个文件夹或文件打 tag（例如标记“这里是 spec”）。然后用 tag 之间的 link 方向约束来定义规则：

```text
omd rule 单向 link <tag> <tag2>     # tag 必须单向 link 到 tag2
omd rule 双向 link <tag> <tag2>     # tag 与 tag2 必须互相 link
```

规则基于 tag，因此新增文件只要属于相应 tag 的范围就纳入同名规则。按 D-32，tag 位于文件或文件夹，规则由 check 统计这些内容的 link 覆盖率，目标为全部应计内容至少被合格范围覆盖一次；不是每个 range 对象都必须另有 link。声明规则不要求立即完成全部实现。

**失败级别（原决定保留，命令归属按 D-32 修正）：** `--level=warn|fail`、默认 fail 作用于用户请求执行的 check 规则；warn 只提醒，fail 表示该项 check 未满足。覆盖不足不是 verify 的强制失败条件。一条规则一个级别，声明后可用 commit 修改；本条不预定具体退出码。

#### 环与传播（用户明确）

range 之间的 link **允许成环**。遍历须终止同一变化的循环传播，又不能合并不同变化或不同 link ID 的处理责任；不能只用一个“已访问 commit”标记吞掉并行关联。commit link 不因成环而拒绝；具体遍历算法不在本条冻结。

#### import commit 的挂载归属（用户明确）

import commit 挂在 **project root 下，是一个单独的分支**，因为它不管理文件 commit。即：project root 下既有文件节点的 init/commit 链，也有独立的 import/exclude/include/tag 分支链；两者同一 project root 但互不混链。

#### dangling 是状态，不是命令

用户纠正：dangling 是一个状态，不是命令。代理在 Q-11 候选默认中列出的 `dangling` 子命令撤回。D-14 中“列出悬空提交”的功能仍保留。

**入口（用户明确）：** `omd list --dangling`。CLI 二进制名为 `omd`。

#### 其他纠正（针对代理候选默认）

- 无效 UTF-8：不是“拒绝作文本模式”，而是按已有决定（AGENTS.md 来源契约）由用户通过 CLI 参数或用户配置指定编码。
- 引用文法中路径只会存在 `/`，不会有反斜杠；代理候选默认中“反斜杠按字面处理”的表述不适用。
- 空文件覆盖率显示 **100%**（逻辑上按 100% 处理，尽管实际是 N/A），避免视觉不规整。

### 多上游、多下游与冲突拒绝

```text
A --+       +--> C
    +--> B -+
X --+       +--> D
```

A、X 的变更已经分别提交，当前内容版本为 A1、X1，B/C/D 尚未适配。A1、X1、B1 等是本例的版本简称，不是 CLI ID、Git 提交或最终存储字段。下表每次成功写入都另行读取并校验该次操作依据的元数据版本；不能在前一步修改元数据后，仍拿同一个旧 hash 连续写入。

| 步骤 | 操作前未处理事项 | 操作及所依据版本 | 操作后未处理事项 | verify 预期 |
| --- | --- | --- | --- | --- |
| 起点 | A1→B、X1→B | A/X 已提交；准备分别处理 | 不变 | 不通过 |
| 1 | A1→B、X1→B | 准备提交 B 对 A1 的适配；读取候选内容后，B 又被编辑，实际 hash 与本次依据不符 | 操作拒绝；不保存该次 OMD 提交，不消除 A1→B，也不以失败操作产生下游提交影响。B 的实际文件改动仍保留 | 不通过，并报告冲突/未提交变化 |
| 2 | A1→B、X1→B；B 有实际改动 | 用户重新读取并复核，显式提交当前 B1；仅选择 A1 的影响，版本校验通过 | X1→B、B1→C、B1→D | 不通过 |
| 3 | X1→B、B1→C、B1→D | 在 B 端针对 B1 的到 D 分支执行 commit clean，说明本次修改不影响 D；使用当前有效依据 | X1→B、B1→C | 不通过 |
| 4 | X1→B、B1→C | C 完成对 B1 的适配并提交 C1，明确选择 B1 的相应影响；本例 C 没有出向关联 | X1→B | 不通过；无需回 B 对已经适配的 C 补 clean |
| 5 | X1→B | 在 X 端针对 X1 的到 B 分支执行 commit clean，说明 B 无需为 X1 修改；核对当前依据，不复用过期读取结果 | 无 | 本例传播检查满足；当前来源采集、覆盖及其他已启用规则也满足时才能整体通过 |

第 1 步拒绝的是 OMD 写入，不是回滚用户在编辑器中的源码改动。第 2 步是使用者重新复核后发起的新操作，不是工具自动换 hash 重试。

没有出向关联的 C 不会凭空产生传播目标，也不需要为了凑 clean 记录添加一次空操作。这不豁免工作流中明确要求 C 存在某类关联的规则；如果该规则缺口存在，整体检查仍不能通过。

此路径在 A/X 的初始提交之外，有四次成功的处理写入：B 的适配提交、B 到 D 的阻断、C 的适配提交、X 到 B 的阻断。读取、校验和失败重试另计；不添加上游回填确认、下游代上游解释或整图盖章步骤。工具不以实际修改顺序推断语义正确，使用者对所选择的适配关系和理由负责。

### reset 产生悬空引用后的 broken 修复

**已确认的行为实例，未执行产品验收。** 假设 A 有 a0、a1 两次提交，B 的 b1 明确记录已经适配 a1，且 B 的旧提交 b0 所需信息仍全部可从当前有效根索引。

| 操作 | 当前有效记录与磁盘数据 | verify / 下一步 |
| --- | --- | --- |
| 初始 | A 当前为 a1；B 当前为 b1，引用 a1 | 假设原关联有效 |
| A reset 到 a0 | a1 仍在磁盘上，但已从当前有效根不可达；b1 及其评论仍在，仍引用 a1 | 警告 B 的 b1 为 broken（脏），列出悬空 a1，并提示可 reset 到 b0 后重建；不能报 all cleaned |
| 查看悬空提交列表及 a1 | a1 可列出并读取，当前有效状态不改变 | 仅查看不修复 B，不自动重放或清理 |
| B reset 到 b0 | b0 成为 B 的有效依据；旧 b1 与评论不被 reset 删除 | 该悬空引用问题解除；若来源内容与 b0 不一致或有其他待处理项，仍须处理 |
| 在当前有效依据上重新 commit | 生成新的 b1-new，而非改写旧 b1；必要引用均可从当前有效根索引 | 本例引用问题已修复；仍须通过内容、传播、覆盖等其他检查才能整体通过 |

D-15 已明确 B0 是文件节点的初始化 commit，且初始化只登记文件自身，不带上游适配依赖。迁移延续节点身份，reset 可沿迁移链选择目标（见「迁移链与回退目标」）。本例以 B0 的挂载路径与必要依据完整为前提；上游适配在后续提交中另行记录，不会把初始化提交一并判为 unreachable_link。找不到合格回退目标时仍如实报告，不伪造目标；是否还存在该情形及其恢复方式，要结合初始化与迁移契约继续核对。

**延伸到间接引用，用户已确认：** 假设 C 的 c1 依赖 b1，原先必要依据完整，且无其他未处理项。

| 时点 | C 的必要依据 | verify 对 B / C 的判断 |
| --- | --- | --- |
| A reset 前 | c1 依赖 b1，b1 依赖可达的 a1 | 本例无引用完整性问题 |
| A reset 到 a0，B 尚未 reset | b1 仍可索引，但其必要依据 a1 已 dangling | B 与 C 均为 unreachable_link；C 的诊断展示 `c1 --> b1 --> a1 (dangling)` |
| B 随后 reset 到 b0 | c1 仍引用旧 b1，而 b1 已悬空 | C 仍为 broken；B 的这项引用问题解除不代表 C 自动恢复 |

直接引用可达并不足以证明依据完整；间接断裂的诊断也不把仍可达的 b1 自动变成悬空提交。上述检查不修改 c1 的原引用，不自动 reset C。

此修复不要求再到 A 补 clean，也不允许以 clean 阻断代替回退重建。来源文件不由 reset 恢复，文件内容检查与引用完整性检查分别报告。

### 迁移链与回退目标

**状态：迁移延续节点身份、reset 可跨迁移链、迁移 commit 含 reason、verify 叶子冲突检测均已确认。追溯：R-06、R-09、R-18、R-20；Q-04、Q-09；D-09、D-14、D-15。**

用户明确：迁移延续同一节点身份，不是路径换行即开始新线路。reset 可沿迁移链选择目标：只要迁移 commit 本身的直接和间接必要依据完整，它就是一个合法的 reset 目标，与其 target 路径是否仍是当前磁盘位置无关——reset 不修改源文件，只移动跟踪状态的有效位置。

```text
B0 (init, target B) --迁移--> C0 (source B, target C) --适配 a1--> C1
                                                                  ^
C1 因 a1 dangling 而 unreachable_link。C 的合法 reset 目标包括 C0 与 B0，前提是各自必要依据完整。reset 到 B0 后，跟踪状态回到 "该文件位于 B"；磁盘上文件仍在 C，这一差异由内容检查单独报告。     a1 (dangling)
```

**迁移 commit 的不可变输入：** 迁移 commit 除 path.source / path.target 外，也包含 reason 字段（每个 commit 都有），属于不可变操作输入，参与 commit hash。

**叶子冲突检测（用户明确）：** verify 会整理每个最新 commit 真实指向的文件路径。如果两个不同的节点叶子都指向同一个文件路径，报告 **conflict** 状态——这也是 broken 的一种。conflict 与 dangling / unreachable_link 并列，作为 dirty 的诊断原因。

### 无理由阻断与外挂评论

对已有 commit c1，用户可通过 note 连续补充说明 n1、n2，形成 `notes [n1, n2]`。两条 note 都直接挂在 c1 上，不把 n2 作为 n1 的子回复；c1 的 ID 和传播效果不因评论变化。

用户若要显式停止当前所选分支，可创建 `commit clean --no--reason`。这是一条新的、有独立 ID 的 clean commit；仅省略理由，并不省略阻断操作或其版本校验。已有 note 不自动代替 clean，clean 也不被 note 操作隐式生成。

### clean、note、unclean、reset 的组合

假设本例所选范围没有其他未处理影响，来源内容从头到尾保持同一版本 H，初始有一条可以显式阻断的传播分支：

| 步骤 | 操作 | 有效跟踪状态 | 提交与评论 |
| --- | --- | --- | --- |
| 1 | 创建 c1：commit clean --no--reason，阻断该分支 | 该分支不再要求下游适配 | c1 是有 ID 的 clean commit，明确省略理由 |
| 2 | 给 c1 添加 note n1、n2 | 不改变步骤 1 的传播结果 | c1 的平面数组为 `[n1, n2]`；不产生状态 commit，不改变 c1 ID |
| 3 | 创建 c2：对同一选定范围 commit unclean，提供理由 | 新增必须处理的脏状态，即使内容仍为 H | c2 与 c1 是不同 commit，不能以 H 相同合并掉 |
| 4 | reset c1 | 有效状态移到 c1，即保留 c1 的阻断结果，c2 不再生效；来源内容仍为 H | 不创建反向状态 commit；c1 上的 n1、n2 不受影响，c2 也不被物理删除 |

此例可以由既有决定确定：c2 生效时存在待处理脏状态；撤下 c2 后不再因 c2 要求处理。整体 verify 仍须检查其他待处理责任、必要引用和来源条件，不能只看 c1 存在便无条件通过；覆盖率另由 check 统计，不是 verify 的强制门槛（D-32）。

若 c2 上也有 note，reset 不删除这些评论；在记录未被另行清理时仍可按 c2 的 ID 查看。之后新增 commit 以本节点有效前驱、新时间戳和随机盐按 D-11 生成新 ID，不把 c2 的 ID 转用于新提交或将 c2 的评论挂到新提交上。

### D-23：显式定向 link 与 ATOMIC 块

**状态：用户确认 ATOMIC 块、begin/end 命令、两方向选项可混用和重复，以及单命令内拒绝同方向同目标的重复关联；单 range 提交链内的自动归属与 verify 闭合检查见 D-25，单次写入与组合操作的发布协议见 E-3/E-6。追溯：D-03、D-08、D-09、D-17、D-22；D-24。**

- 用户明确：不从文本猜测 link，必须显式 link 才算关联。适配选择与创建关联是不同动作；理由里出现某个 ID 不构成创建 link 的授权，也不能据此改写历史记录。已有 range 之间的 link 随范围后续提交保持其身份，不属于自动创建新 link（D-24）。
- 用户提出将多个 OMD commit 打包为 **ATOMIC block（原子块）**。块沿单条 range 提交链按顺序分组，以 begin/end 约束整体的 reset 边界，并由 verify 检查闭合。D-26 已明确块内提交立即推进当前版本，不等待 end；此前代理补出的“end 前不生效、失败必定自动全部撤回”不能当作已确认契约。块内操作失败保留此前已成功记录、不自动撤回或补 end；单次发布完整性见 E-3，不承诺撤销用户的磁盘编辑或外部来源命令的副作用。
- 用户选择命令 `omd commit atomic begin` 和 `omd commit atomic end`。begin 对应块开始前的特殊 commit 点，end 对应整块完成后的特殊 commit 点；end 关闭该块，不是取消，也不是此前全部提交第一次成为当前状态的时点（D-26）。
- 内部仍是多个 commit，而非把理由、操作及身份压成一个普通范围提交。块内普通成员 commit 不能被单独 reset；任意层级 begin/end 是可选择的占位标记，按 D-27 退一步。对普通内部成员的请求必须报错，给出所属块的 begin/end commit ID，引导用户选择边界，不能自动把目标改为最近边界。边界仍须满足既有 reset 和必要引用校验，不能借此恢复不可用的历史。
- 常用操作提供组合简写，遵守与显式原子块相同的检查。提交范围 B 的修改时可显式加 `--link-from <range>` 或 `--link-to <range>`：from 创建所指定范围到 B 的关联实例，to 创建 B 到所指定范围的关联实例，每个实例有自己的 link ID。范围提交与所选新 link 在同一条范围链的 ATOMIC 块中依次记录，成功完成组合操作须写入 end 闭合。已有 link 上的适配须指定其 link ID 和理由，不要求重新创建 link；新建另一个 link 也不会自动处理旧 link 的待办。这里 `<range>` 仅表示端点范围，不冻结范围定位参数的编码形式。

```text
BEGIN [s]
  range B commit [b2]        record a content change
  link commit               create L1: range A -> range B
END   [e]
```

简写表达“提交范围修改并显式创建关联”，不表示“每次适配必须重建关联”。适配已有 link 的对应规则见 D-24。

**多目标及防误操作（用户后续确认，按 D-24 的 range 对象解释）：** 两种参数可以在同一命令中同时使用，也都可以重复指定不同目标。仅拒绝同一命令内重复的“方向 + 端点范围身份”，如 `--link-from A --link-from A` 或 `--link-to A --link-to A`；报错而非静默去重，不留下该命令部分生效的范围提交或 link。`--link-from A --link-to A` 是两条相反方向的关联，不属于重复。不同合法输入若定位到同一个 range，也不能因文本或版本不同绕过检查。这是单命令参数校验，不是全局按端点去重：用户可以在不同命令中明确建立同方向、同 source/target range 的 L1、L2，用 link ID 区分。必要引用与版本检查照常适用。

**术语依据：** SQL Server 的原生编译存储过程采用 `BEGIN ATOMIC ... END`；无外层事务时，正常退出提交，未处理的异常回滚块。显式事务另用 `BEGIN TRANSACTION` / `COMMIT TRANSACTION` / `ROLLBACK TRANSACTION`。本设计只借用原子块术语，不引入 SQL 依赖、SQL Server 的嵌套/保存点规则或自动分布式事务。来源：[Atomic Blocks](https://learn.microsoft.com/en-us/sql/relational-databases/in-memory-oltp/atomic-blocks-in-native-procedures)、[BEGIN TRANSACTION](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/begin-transaction-transact-sql)。

**对既有 reset 的限定：** D-09、D-16、D-22 及范围/文件回退要求必须同时满足本条的块边界限制；它不是第四种标记状态。D-25 已确定块只沿一条 range 提交链分组，不涉及把多条节点前驱链并成一个事务；文件 reset 若需恢复任一子范围到块内普通成员，按 D-22 整次拒绝；这不扩大为禁止直接选择内层 begin/end。

### D-24：link 以 range 为端点，以 link ID 区分关联实例

**状态：用户直接纠正并确认。追溯：D-03、D-08、D-14、D-17、D-23；解决原 OQ-P2 的错误建模问题。**

用户明确：“我们的 link 是基于 range 的 link，而不是你想象的 commit 节点的link”；随后补充：“link 也需要一个 link id，这样才能处理多个一样的方向的一样的 target source 的 range 的 link，然后之后如果做适配，也需要写 id 再加理由，不然都不能一一对应”。

- **range 身份与版本分开。** a1/a2/a3 是同一范围 A 的提交版本，b1/b2 是同一范围 B 的提交版本。关系端点是 A、B，不能因出现新 commit 就把一个既有 link 拆成多组独立版本边；坐标相同的独立 range 仍是不同对象。
- **link 有自己的持久身份。** 每个显式创建的关联实例有可区分的 link ID。允许 L1 和 L2 都表示 A 到 B，不能全局按 source、target、方向合并或拒绝它们；但仍按 D-23 拒绝同一命令中的重复创建参数。
- **版本推进不重建关系。** L1 在 A/B 正常追加范围提交后仍是 L1。已有关系的持续跟踪不属于从文本猜 link，也不要求每次适配重新 link。再次显式创建相同端点的 L2，是另一个用户操作，不是版本更新的隐式结果。
- **适配一一对应到 link。** 适配必须显式指定处理的 link ID，并提供与之对应的理由；不能只凭端点、理由文字或“这里只有一条 link”推断目标。处理 L1 不自动处理同端点的 L2。D-08 的部分变化选择继续有效：点名 L1 也不自动处理该关系上未选中的其他变化。
- **关系身份不替代版本依据。** commit 仍记录某次操作和复核所依据的版本；必要依据悬空的 D-14 诊断与修复规则不因此取消。不能因为 A/B 两个 range 仍存在，就擅自换用新版本来修复失效的依据。
- **ID 与参数边界。** link ID 不是“当前 range commit ID”的别名。link ID 的生成/持久化格式、范围定位格式，以及适配选择 link ID 的具体 CLI 参数拼写仍待工程规格化；现有 `commit --id` 的范围版本选择不能被悄悄挪作 link 选择。

#### 持续跟踪例子（纸面核对，非执行结果）

仅有 L1：A 到 B，a1/b1 是最初的当前版本，没有其他未处理事项。A 提交 a2 后，B 有沿 L1 处理这次变化的责任；用户提交 b2，明确指定 L1、相应变化和理由，处理该项责任，无须另建 link。A 随后提交 a3，沿同一个 L1 产生新的待处理变化，不因历史版本 a1/a2 产生额外 link。若用户另外创建了 L2：A 到 B，L2 是另一个关联实例，其责任不能被 L1 的适配一并消除。

此前将问题问成“a1→b1 的旧 link 与 a2→b2 的新 link 哪个继续生效”采用了错误前提，现撤回；不将未获选择的两个选项写成产品规则。

### D-25：ATOMIC 沿单个 range 的提交链自动归属

**状态：用户直接确认。追溯：D-09、D-22、D-23、D-24；OQ-P7 的归属与范围问题已解决。**

用户明确：“start 到 end 中间的 commit 都是自动加入的，verify 会检查 ATOMIC 是否用 end 块闭合了，因为我们的 ATOMIC 设计是只在一个 range commit 的路线上 ATOMIC，所以我们没有所谓的并行修改的问题”。命令名称仍沿用已确认的 `omd commit atomic begin/end`。

- 每个块只位于一条 range 提交链上。同一条链在 begin 与对应 end 之间的 commit 自动成为块成员；不按 shell/终端会话或整个元数据存储推断成员，也不增加先前候选的 `--atomic <块 ID>` 参数。
- **嵌套（用户补充确认）：** 同一条链允许块内再 begin；end 关闭最近尚未闭合的 begin，关闭内层不等于关闭外层。任一层尚未闭合，verify 仍报告闭合失败。嵌套边界 reset 统一遵守 D-27，不引入外层边界的额外限制。
- 块内的 link 等操作必须属于这条范围提交路线；关联的 source/target 可涉及其他 range，但不会因此把对方的提交链纳入本块。该设计不引入跨 range 的多链原子修改或分布式事务。
- `verify` 检查 begin 是否有对应 end 闭合。发现未闭合块时报告结构不完整，不能把该项检查或整体验证报告为通过；不能自行补 end 或把已写入的部分记录当作整块成功。闭合通过也不等于内容、适配或其他有效性检查通过，更不代表另行执行的 check 已有 100% 覆盖。
- 自动归属、当前状态推进和闭合检查分别按 D-26 解释；不新增范围标记状态，也不取消单写者与旧版本冲突拒绝。不能因为块尚未闭合，就把已经写入的范围提交假装成尚未生效的隐藏草稿。
- 通过 reset begin 撤下未完成块的开始点及后续记录，见 D-27；不能另加未经选择的取消命令。嵌套与文件 reset 的内部目标拒绝已由用户补充确定（D-22、D-27）。中途失败保留已成功提交，不自动补 end 或重试；用户可显式继续该链并闭合，或按既有边界规则 reset。begin/end 的范围选择语法及单次写入的崩溃恢复进入工程方案。

```text
range B: b0 -> BEGIN -> b1 -> link operation -> b2 -> END -> b3
                        [ automatic block membership ]
```

### D-26：未闭合块推进当前状态，但不放开内部 reset

**状态：用户明确选择并再次强调 reset 边界。追溯：D-09、D-22、D-23、D-25。**

给定范围 B 的链为 `b0（10～20）-> BEGIN -> b1（10～30）`，尚无 END，用户选择：“当前已经是 10～30”。随后强调：“reset 必须只能是原子commit 的 start 或者 end，不能reset中间的commit”。

- 块内每次成功 commit 都照常推进该 range 的当前状态。此例中 b1 不只是可查看的暂存记录；B 当前就是 10～30。
- `verify` 因缺少对应 end 而报告块未闭合，不能通过该项检查。写入 end 后，闭合检查可以通过，范围仍为 10～30；其他内容与适配检查不因此自动通过；内容/link 覆盖率另由 check 统计。
- ATOMIC 内部的普通成员 commit 不能作为单独 reset 的目标，即使它已经是当前版本，或块尚未闭合。begin/end 是特殊边界，按 D-27 的后续补充在任何嵌套层级都可作为目标；错误提供真实边界 ID，不自动替用户选择边界，不编造尚不存在的 end。
- 这些是不同约束：当前状态可以前进，结构验证仍可失败，而 reset 可选点只在边界。未涉及原子块的普通 reset 继续遵守既有要求。
- 撤回此前“所有块内操作都等 end 才发布为有效状态”的代理推论。失败不自动撤回已成功提交、不补 end、不重试；显式继续或 reset 按 D-25/D-27 处理。单次记录写入的崩溃完整性仍属工程契约，不套用 SQL 的整块回滚。

### D-27：reset 特殊边界落在其前驱，并必须警告

**状态：用户明确修订特殊目标规则；普通 reset 语义不变。追溯：D-09、D-22、D-23、D-25、D-26。**

用户明确：reset 到原子提交的 start 或 end commit，都会退到该点的前一个 commit，不停留在这个特殊标记上；普通 commit 才停在目标本身。由于行为不同，原子边界 reset 必须额外发出 warning，避免误解。

**核心理由（用户补充明确）：** begin/end 是占位标记符 commit，本身不提供独立的正文/业务恢复状态。reset 撤下所选占位标记及其后续记录，因此以该标记的直接前驱作为有效落点；这才是 `-1` 的原因，不是为嵌套另设回滚算法。标记仍承担块归属和闭合检查的结构作用，“不是独立正文版本”不等于可以忽略它的结构记录。

**可复用的设计原则：** 后续若新增同类占位 commit，可参考“撤下所选标记、保留其直接前驱”的规则，但须明确该类型是占位标记及其结构作用；本轮不新增提交类型或通用扩展机制。不能仅凭内容为空或未改变就判断为占位：clean、unclean、适配等仍有实际状态作用。`-1` 只沿 previous_id 移动一步，不按时间排序，也不递归跳过前驱中的其他标记。

- **按请求目标类型处理。** 块外普通目标保留本身；begin/end 目标按同一范围链的直接前驱确定实际落点，不按时间戳猜前后。块内普通成员仍不能被直接指定为 reset 目标。
- **嵌套不增加特殊回退规则（用户补充确认）。** begin/end 无论处于哪一层，都先按特殊边界处理，不能因为它同时处于外层块内部而拒绝。前驱可以是普通成员，也可以是另一个边界；不跳过前驱、不跳到外层起点。例：`b0 -> begin s1 -> b1 -> begin s2 -> b2 -> end e2 -> b3 -> end e1`，reset s2 落在 b1；reset e2 落在 b2；直接 reset b2 仍拒绝。闭合情况按回退后的有效链重新检查。
- **特殊标记一并撤下。** 成功 reset begin/end 后，从该标记开始的后续记录退出当前有效历史成为 dangling，原记录和 note 保留，不物理删除，不追加反向 commit，不改磁盘文件。
- **开始点示例：** `b0 -> begin s -> b1` 尚未闭合时，`reset s` 落在 b0，s 与 b1 一并撤下。当前范围恢复 b0 的状态；当前有效链中已无这个 begin，因此 verify 不再为它要求补 end。其他内容/引用检查照常进行。
- **结束点示例：** `b0 -> begin s -> b1 -> end e` 中，`reset e` 落在 e 的直接前驱 b1，撤下 e。这保留块内已发生的修改，却重新留下尚未闭合的 begin，因此 verify 报未闭合。它不等于直接允许 `reset b1`；也不能擅自把 `reset e` 改为退到 b0。
- **warning 必须说明差异。** 执行特殊边界 reset 时，额外提示请求的边界 ID 与实际前驱落点，说明它不同于普通 reset；JSON 输出同样提供该警告。若实际落点不能满足必要依据/版本等检查，仍拒绝操作，不能假称回退成功。

此前代理提出的“保留 begin，再将块标为已放弃”与“保留 begin 后要求补 end”两个选项都不是用户选择；实际规则是将 begin 自身撤下。闭合检查针对当前有效链，不能因 dangling 历史里仍保留旧标记而报当前块未闭合。

#### 组合核对：范围版本、link 实例与块边界

**状态：由 D-08/D-09、D-24～D-27 推导的纸面核对，不是新增用户选择，也不是产品测试。**

固定对象：A、B 是范围；a1 是 A 的当前版本；b0、b1 是 B 的版本；s、e 是 B 链上的 begin/end 标记；L1、L2 是两个同方向、同端点 A 到 B 的独立关联实例。L1/L2 的创建记录都在块之前有效，b0 时两者各有一项针对 a1 的待处理责任。b1 将 B 的范围从 10～20 改为 10～30，并显式指定 L1、a1 的这次变化和理由完成适配，未选择 L2。全程没有其他来源变化；L2 没有依赖本次将被撤下的记录。

| 路径 / 步骤 | 当前提交 / 实际落点 | B 当前范围 | 当前有效 link | 本例待处理责任 | 闭合检查 | warning | 退出有效历史但保留的记录 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 起点 b0 | b0 | 10～20 | L1、L2 | L1、L2 均待处理 | 无未闭合块 | 无 | 无 |
| 写入 s、b1，尚无 end | b1 | 10～30 | L1、L2 | L1 已处理；L2 待处理 | 失败：缺 end | 无 | 无 |
| 正常写入 end e | e | 10～30 | L1、L2 | L1 已处理；L2 待处理 | 通过 | 无 | 无 |
| 从完整链请求 reset e | b1 | 10～30 | L1、L2 | L1 已处理；L2 待处理 | 失败：e 已撤下，s 仍有效 | 请求 e，实际 b1 | e |
| 从完整链请求 reset s | b0 | 10～20 | L1、L2 | L1 恢复待处理；L2 仍待处理 | 无该未闭合块：s 已撤下 | 请求 s，实际 b0 | s、b1、e |

后两行是从同一完整链 `b0 -> s -> b1 -> e` 出发的两条替代路径，不是连续执行。闭合检查通过不代表整体 verify 通过：本例 L2 始终尚有待处理责任。reset s 撤下的是 b1 中针对 L1 的适配证据，不是 L1 在块前已有的创建记录；L2 不因端点相同而被处理、删除或改变对应结果。记录和 note 仍可查，但撤下的适配不能继续计为当前已处理证据。

**创建操作的对照：** 若改为 L2 在块前已存在，而 L1 的创建操作首次记录在此块中，reset e 只撤下结束标记，L1 的创建仍有效；reset s 则撤下 L1 的创建记录，L1 不再计为当前有效关联，其创建记录及 link ID 保留在历史中。L2 不因与它同端点而退出有效关联。若另有有效记录的必要依据指向被撤下的版本，仍按 D-14 报 unreachable_link；“不能按端点连带处理”不等于豁免真实的引用失效。

这些结果由操作记录是否仍在当前有效历史中决定，不要求选择快照或重放实现，也不新增取消状态。

### D-28：command 只替换内容取得方式，初始化即采集，以所属项目根执行

**状态：用户明确确认首次采集与 cwd，并补充与文件共用全部跟踪逻辑。追溯：R-14、R-15、R-18；D-05、D-16；OQ-P3 的产品流程已明确。**

用户补充：“逻辑跟文件一样，只是一个是读文件内容一个是命令输出，别的完全没有区别”。因此 command 不是第二套跟踪流程；执行许可、argv、退出码和 stderr 等差异只属于内容取得这一环节，取得完整成功内容后共享文件的 hash、Myers、range、link、适配、ATOMIC、reset、历史、持久化及缓存规则。

- 用户显式初始化 command 对象时，执行已选定的固定 executable 和字面 argv 一次，取得首个完整 stdout。正常退出且 exit code 为 0，并满足其余写入前置检查后，才产生初始化 commit，保存完整成功输出。
- 启动失败、异常退出或非零退出时，初始化失败，不产生初始化 commit，也不把部分 stdout 记为首个成功来源版本。空 stdout 且 exit 0 仍是合法内容，stderr 独立诊断；成功采集不会自动确认 range。
- 显式执行 command 初始化操作是这一次首次采集的许可。`VERIFY_COMMAND_AUTO_RUN` 及本次参数控制 verify/check（后者由 D-32 补充），不阻止用户显式请求的初始化采集；读取登记信息、历史或重建缓存仍不是执行许可。
- 初始化采集与以后获准的 verify/check 采集，都以该 command 所属项目的本地根目录作为 cwd。它不是外置 OMD 元数据目录，也不随用户调用 omd 时所在子目录变化。所属项目根不可用时报告执行上下文/启动失败，不偷偷换到调用目录运行。
- 不另设 command 专属的提交、确认或回退生命周期，也不因输出采集成功而放宽文件式复核要求。初始化失败不表示可以撤销外部程序已发生的副作用。
- 进程 I/O、环境/PATH 与资源处理的必要工程默认应在内容读取实现方案中明示，与文件读取共同审查；当前没有选定额外数值限额、配置开关、交互协议或执行途径。不得把这些细节扩展成另一套产品流程。

### D-29：可选 git 来源复用已提交对象取得历史内容

**状态：用户确认 Git 对象复用、不另存内容及缺失时报错；当前文件观察按后续明确的 D-31 执行。追溯：R-04、R-09、R-20；D-06、D-22、D-28。**

用户希望用 Git 中已有的版本替代内容副本，并关联 Git commit ID 与 OMD commit ID。“只读已提交内容”限定的是 Git 所提供的那个版本，不能扩大成 verify 不观察工作区未提交变化。确认的取舍如下：

- 与 file、command 并列保留显式 git 内容来源，供已记录版本从本地 Git 提交取得完整内容。未提交的 Y 不能被冒认成历史 Git 版本 G1 的 X，但真实文件当前的 Y 仍须按登记路径读取和检查。不能仅因目录存在 Git 仓库就暗中改换历史保存方式。
- 每次记录 Git 来源版本时保留确切 Git commit ID、仓库定位和该版本中的文件定位等必要元数据，形成与 OMD commit 的可追溯关联。两种 commit ID 各有用途，不合并为一个身份，也不假定一一对应；浮动 ref 名称不能代替历史版本的确切 ID。
- git 来源不再由 OMD 备份一份完整内容；旧内容从所引用的本地 Git 对象恢复。必要定位信息仍保存在权威文本中，不能只在 SQLite 缓存里。删除 OMD 缓存但仓库对象完好时仍可恢复；仓库或对应对象丢失时必须报告来源版本不可取得，不能靠 hash、当前工作区或另一个 Git 版本伪造旧内容。
- **对原恢复保证的明确限定：** D-22 中 file/command 的完整内容保存与无 Git 恢复保证不变；选择 git 来源则接受依赖其仓库及历史对象的代价。理由是减少重复内容保存，并便于追溯已有 Git 版本。这不是把所有来源的历史都交给 Git。
- 取得内容后仍按 D-28 的统一文件式逻辑处理：内容 hash、Rust 内 Myers、range、独立 link ID、适配、ATOMIC、reset 与 note 规则不变。不能仅因 Git commit ID 改变就认定文件内容或全部 range 变脏；不会使用 Git diff、index 或 changed-files 替代已有判定。
- 该可选来源需要本地 Git 内容读取能力，但不改变普通项目的根识别、项目身份或非 Git 工作方式。此决定不授权自动 Git commit、checkout、clone、fetch、git gc 或创建保护 refs；读取一个来源不等于管理用户的 Git 历史。

**依据与边界：** [git-show](https://git-scm.com/docs/git-show#_examples) 支持按提交和文件定位读取历史内容；[git-gc](https://git-scm.com/docs/git-gc#_notes) 的对象保留依赖 Git 自身 refs 等可达性，OMD 文本中保存一个 ID 并不自动保护对应对象。用户已选择接受 Git 对象缺失时报错的边界，不把来源记录误称为内容备份。

Git 历史内容引用的语法、本地仓库和版本内文件定位仍需明确，见 OQ-P8；真实文件当前内容按登记路径读取已由 D-31 确定，不再等待 HEAD/ref 选择。此前 `git:github.com/...` 仍只是项目身份标识示例，不能未经定义就当作 Git 历史内容引用或联网指令。

### D-30：replace 转换来源，只接受同一完整内容版本

**状态：用户确认 file、command、git 可相互 replace，不通过新增 OMD commit 叠加来源设置；随后明确选择内容不同时拒绝。追溯：D-11、D-22、D-28、D-29。**

用户的用途是先用 file 保存临时内容，待用户自己完成 Git 提交后，改用 Git 取得同一份内容。对“目标 Y 与已记录 X 不一致”的问题，用户选择“不同内容就拒绝”。

- replace 是来源转换，不是内容变更提交，不新增 `commit set` 或其他来源设置 commit。转换不重建跟踪对象，不改已有 OMD commit ID、原始不可变操作输入、range 身份、link ID 或 note。
- 新来源必须提供被替换版本的同一份完整内容，不能仅比较选中 range 的片段。完整内容不一致时拒绝本次 replace，原绑定、内容和历史保持不变；不降级为“仅切换后续读取，留待 verify 处理”。
- 典型核对：O1 原来保存完整内容 X；本地 Git 的 G1 在指定文件位置也保存 X。成功转换后，读取 O1 的历史内容时从 G1 的该文件取得 X，并保留 Git/OMD ID 关联；O1 的 ID、时间、原始输入与范围/关联身份不变。真实文件的当前观察仍读取当前登记路径，不因这次转换改为读取 Git 树（D-31）。
- 反例一：G1 只保存 Y 时，不能把它改挂到 O1 冒充 X，即使所选 range 的片段恰好相同也拒绝。反例二：更早的 O0 保存 Z，却没有对应 Git 内容时，不能把 O0 也指向 G1；其原有完整恢复依据必须保留。转换成功不等于全部历史都已迁移。
- “临时副本后转 Git”不授权自动清除副本。若原副本仍被其他版本或对象需要，尤其不能移除；具体释放方式尚未确定，不以减少复制的意图代替清理授权。
- 仍遵守单写者及旧版本/hash 不匹配即拒绝的约束；不自动改用新 hash 重试，不运行 Git 提交或联网操作。command 的来源转换也不能借此越过已确认的执行许可边界。

这些是转换的行为约束，不预先规定存储分层或物理布局。replace 的目标选择、涉及 command 时的采集许可与副本释放方式仍须写清，见 OQ-P9；不再重问已确定的内容不一致处理方式。

### D-31：真实文件看当前路径，Git 提供记录中的旧版本

**状态：用户最新明确澄清，纠正代理对当前观察的错误限定。追溯：D-16、D-22、D-28～D-30。**

用户明确：“默认就是只是去看文件路径指向的那个文件现在的样子，不关心是 HEAD 还是啥”。此前代理将问题限为“跟随 HEAD / 固定 Git 提交”，用户在该选项中选过 HEAD，随后作出上述澄清；以最新澄清为准，不把 HEAD 选择写成当前观察规则。

- 对真实文件，verify 默认读取当前登记路径所指文件的完整现状，包括未提交修改。当前内容不由 HEAD、分支、index 或 Git 状态列表决定。
- 已记录的旧内容仍按该记录的版本依据取回。O1 的 X 若已转换为 Git 引用，仍从确切的 G1 和记录中的文件定位取得；HEAD 变化不能使 O1 改读另一个版本。
- 连续例子：O1 保存 X，先以同内容 replace 改由 G1 提供；随后路径上的文件变为未提交的 Y，HEAD 仍为 G1。verify 比较 G1 的完整 X 与路径上的完整 Y，按 hash/Myers 判断受影响范围；O1、link 和 note 身份不变，不自动追加 OMD 或 Git commit。
- 当前路径消失且没有 tombstone 时，仍报告 missing；Git 中保留历史 X 不能充当当前文件。反过来，当前文件存在也不能冒充已经丢失的历史 Git 内容。
- replace 拒绝把既有 X 换成不同的 Y，与 verify 观察 X 到 Y 的正常变化是两回事。不能用前者屏蔽未提交变化，也不能用后者放宽历史替换条件。
- 这项澄清不要求虚拟 command 对应一个真实磁盘文件。它仍按已确认的执行许可取得完整当前 stdout，并使用保存的历史输出作旧内容；不因修正 Git 规则而新增执行许可或重复运行。

这里只明确比较时旧内容与当前内容的位置，不新增对象层次、存储分层或来源生命周期。

### D-32：check 按内容统计覆盖率，不作为 verify 的强制门槛

**状态：用户明确纠正 tag 检查粒度及命令归属。追溯：R-06、R-07、R-10；D-02、D-17、D-24。**

用户明确：“spec 和 code 是标记在文件或者文件夹上的，所以我们必须要求spec到 code 文件/文件夹的link率是百分之百，也就是文件或者文件夹里的百分之百的非空内容都被至少标记一次”。随后补充：“当然这不是强制的 verify，它算 check 命令，check 命令是跟测试覆盖率一样，我们这种叫做内容覆盖率，也是 link 覆盖率”。

- **命令分开。** check 按被检查的内容统计覆盖率；针对 tag 关联要求时称为 link 覆盖率。覆盖不足不是 verify 的强制失败条件。verify 保留变化检测、既有责任、必要引用、来源及 ATOMIC 闭合检查；不能反过来把 check 的 100% 当作这些检查通过。
- **分母是内容，不是对象数。** tag 属于文件或文件夹，检查其中应计的全部非空内容。100% 表示这些内容的每个计数单位都至少被覆盖一次，不是每个文件有一条 link 即可，也不是每个 range 都必须单独有 link。目录内没有任何 range 的新内容同样属于覆盖缺口，不能仅枚举已有 range 后声称全覆盖。
- **关系通过范围表达。** link 端点仍是 range。对选定的 tag 关系，只有符合该关系要求的有效范围关联才能贡献相应 link 覆盖；单独存在标记而没有对应关联，不能冒充这条关系已覆盖。这里明确计数依据，不额外规定必须输出两套独立指标或报告模式。
- **至少一次只计一次。** 多个合格范围可以共同覆盖全文，重叠部分只计一次；不能用重复 range 或同端点多个 link ID 填补其他位置的缺口。只有未过期的已确认范围可贡献有效覆盖。某处存在合格覆盖，不意味着同位置其他独立 range 或 link 的待处理责任已被完成（D-24）。
- **例子（纸面，不是执行结果）。** 被检查的 spec 内容为 `ABCD`，其中只有 `AB` 具有到 code 的合格关联，`CD` 尚未关联：这条 link 覆盖检查不能报告 100%。重复标记 `AB` 或增加覆盖同一部分的平行 link 都不能补足 `CD`。即使本条 check 未达 100%，只要 verify 自己的条件满足，verify 也不因覆盖率不足失败。
- **已有操作边界保留。** check 不自动创建、确认或修复范围/link，skip 不变成覆盖，空文件仍显示 100%。原 warn/fail 级别在用户执行相应 check 时适用，不自动安装为 verify 门槛。check 同样支持 --json，不因调用它就授予来源命令额外执行许可。

**文本空白计数（用户补充确认）：** 用户选择“空白不计”：空格、制表符、换行等空白字符不进入文本覆盖统计。文本依次为 A、空格、B、换行时，A、B 都有合格覆盖即为 100%。这是统计过滤，不删除原文，不改变坐标、hash、Myers 比较或 replace 的完整内容相等要求。由空白不计和空内容显示 100% 可直接推出：全空白文本的应计内容为零，同样显示 100%。byte 模式不套用文本空白过滤，不能据此剔除零字节。

**tag 与采集衔接（用户补充确认，关闭 OQ-P4）：**

- 目录 tag 递归继承并叠加，包含之后新增的成员；文件或子目录增加 tag 不替换祖先 tag。例如 `docs/` 为 spec、`docs/examples/` 再加 example，其成员同时属于 spec 和 example。相同 tag 继承多次仍是同一 tag，不重复计算同一内容。import/remove/exclude/include 的统计范围规则不变。
- `spec -> code` 只要求该方向覆盖，不禁止额外 `code -> spec` link。双向规则分别要求两个方向达到完整覆盖，不能用反向查询冒充反向 link。
- check 接受 `--run-command` / `--run-command=false`，优先于同一个用户配置 `VERIFY_COMMAND_AUTO_RUN`，内置默认仍为 false。仅在这套许可允许时采集检查范围内 command；未采集或失败时不能以旧输出冒充当前覆盖。完整 stdout、正常 exit 0、所属项目根和单次采集复用规则与 verify 共用。

具体字符分类的标准库选用属于工程落法，不另设新的产品统计模式。

### E-1：范围、坐标与覆盖（ED-01～06；OQ-P5）

- 坐标采用 0 起点、左闭右开 `start:end`，允许 `start == end`，要求 `0 <= start <= end <= 来源长度`。文本按解码后的 Unicode scalar value，byte 按原始字节；换行、BOM 和原始编码不被统计规则改写。编码优先级为本次显式 `--encoding` > 此跟踪已记录编码 > 文件配置 > 项目默认 > 用户默认 > UTF-8；每次提交记录实际采用的编码，配置变化不能重新解释历史坐标。
- 按 D-32 只在覆盖统计中过滤文本空白，采用 Rust `char::is_whitespace` 的 Unicode White_Space 定义；byte 计入所有字节。分子为合格覆盖在应计位置上的并集大小，分母为所选来源的应计位置数，分母为零显示 100%。跨文件合计先加计数再除，不平均各文件百分比；文本和 byte 分开统计，避免混加不同单位。
- 完整旧新来源用 Myers 比较；仅未受正文变化、位置迁移或边界插入影响的范围保留确认。纯插入恰好位于范围结束处也使旧范围变脏，理由是无法确认新增内容与原范围无关；不自动扩大原范围或确认新增文字。范围内插入/删除、变更穿越边界及位置迁移均须复核，只给候选而不自动写新 commit。相同最短编辑路径或重复片段不能作为对象身份已证实的依据。
- 无可靠定位时，保留原范围和旧版本，报告旧坐标、差异及可用候选，用户用 `commit --id <当前范围提交> --range <新坐标> --reason <理由>` 明确选择；不能自动选另一处同文片段。拆成多段时仍不自动创造范围身份：用户可保留一个连续范围，或在原范围保留一段并显式新建其余跟踪；新范围不继承 link。
- **正文全部删除的入口：** 用户在仍存在的来源中显式提交 `--range p:p --reason "该段已删除"`。这是同一范围的一次正常新版本，保存完整当前来源，贡献零覆盖；保留范围/link 身份并按普通变化处理下游。空范围可表达已删除的内容，但不能作为非空内容的合格对应证据，不能通过把非空范围连到空目标来填满 link 覆盖。它不是文件 tombstone，也不自动处理断裂的必要引用。不接受通过 clean/note 消除无法解释的坐标错误。缺失整个来源仍按 missing/tombstone 处理，不伪装为空来源。
- 验收重点：多字节文字、LF/CRLF、空范围、全删、重复片段、重叠独立责任；空白过滤前后的 hash/Myers 输入完全相同。文本/byte 混合不报告无单位的合并百分比。

### E-2：记录、身份与 canonical hash（ED-07、11、12）

权威元数据继续采用 TOML，完整来源保存原始字节。持久布局如下；state 只是物理发布点，不新增全局业务提交链或第四种状态：

```text
<metadata-root>/
  omd-manifest.toml       固定格式标识，仅用于发现元数据目录
  root.toml              已确认的虚拟根记录
  registrations/<id>.toml 不可变的存储/项目/alias 登记版本
  state.toml             当前 tip/挂载/登记/绑定索引、保留记录清单、发布代号
  commits/<id>.toml      不可变原始提交输入及内容引用
  versions/<id>.toml     完整来源长度/hash、解码信息与原始采集信息
  content/<sha256>       file/command 的完整原始字节，可共享
  bindings/<id>.toml     不可变的某次恢复定位；state 选择各版本当前 binding
  notes/<id>.toml        平面 note/add/patch/delete 记录
  inbound/<id>.toml      跨存储引用的持久保护凭据
  pending/              未完成写入；不是有效提交或成功采集
  write.lock            固定锁文件，不靠删除文件解锁
```

- 文件/range/import 的稳定对象标识为其链的首个 commit ID；首个记录不把自身 ID 放入 hash。后续沿 previous_id 解析同一对象。父级挂载引用父节点的 commit 身份，不用 project_id 代替。文件提交保存当时的 `range_id -> tip` 表，项目级提交同理记录其恢复所需的挂载版本，不按时间戳猜历史。
- 存储登记使用独立随机 128-bit store_id，属于位置/归属元数据，不作为 commit hash 的附加输入。来源版本也使用独立随机 128-bit ID，先于引用它的 commit 创建，避免初始化 ID 自引用；记录完整字节 hash、长度和采集描述。相同来源定义、解码视图及内容的重复观察可复用已有来源版本，不为检查时间制造新版本；不同版本可共享同一 content 文件。来源版本 ID 与业务 commit ID 不混同，unclean 等新操作仍各有新 commit。
- link 使用独立随机 128-bit ID，创建记录保存其身份、方向、端点范围及选定版本依据。note 同样有独立 ID；patch/delete 另建记录并引用被修订 note，不改原记录。note 保存 `id, timestamp, commit_id, kind, target_note_id, text`，由发布记录保留追加顺序，不能按可变时钟猜修订先后。本轮不增加 author、回复树或审批字段。ID 碰撞拒绝覆盖并重新生成。
- 每个 commit 保存 `schema, kind, salt, previous_id, timestamp, content_ref, operation_payload`；其中 schema、kind、content_ref 也必须纳入 canonical payload，顶层同名字段仅是须校验一致的索引投影，不能留下可改变提交含义而不改变 ID 的旁字段。payload 依操作类型封闭定义字段，包括路径/坐标、理由或显式无理由、端点/所选变化、expected 节点版本与来源 hash。字段未知、必填缺失、重复键、越界整数均报错，不凭扩展字段猜行为。TOML 无 null 时用显式 variant 表示，转换成统一逻辑值后再计算 ID。
- content 字段是操作所用完整原始来源字节；range 从引用版本取完整内容，不只 hash 片段。BEGIN/END 等纯结构标记没有新正文时使用空 content，必要继承依据由 payload 的版本引用表达。其他无正文变化但有状态作用的提交不能因此变为占位类型。
- 固定编码：盐为 16 个 OS CSPRNG 生成的 `[A-Za-z0-9]` ASCII 字符，直接置首；其后 previous_id、timestamp、content、canonical payload 各用 `u64 大端字节长度 + 原字节` 分帧。previous_id 首条为空字符串；时间戳统一 UTC RFC3339 纳秒表示，`--timestamp` 接受显式值且不要求接近当前时间。payload 用 RFC 8785 JCS；大整数（坐标、长度等）编码为十进制字符串，避免 JSON 浮点丢精度。不归一化用户文字。

```text
id = SHA256(salt_ascii_16 || frame(previous_id_utf8)
           || frame(timestamp_utf8) || frame(full_content_bytes)
           || frame(JCS(operation_payload)))
```

- 对象 ID 在所选权威存储内解析；跨存储端点记录目标 store_id 与范围首提交 ID，本地端点使用 local 作用域，避免将本存储归属塞进 hash。复制记录保留原输入，引用不会因同名 alias 自动指向新副本。project_id 及本机归属、可变别名映射、note、缓存、派生状态不进入 hash，也不把包含它们的 manifest hash 塞进 payload；外部引用的目标 store_id 是解析命名空间，不是 project_id。物理发布代号/登记前置条件独立校验，payload 的 expected 值只包含相关节点 commit ID、必要内容 hash。replace 只改恢复 binding；复算使用确切旧内容，不查询当前项目归属。
- 验收重点：黄金字节向量、不同字段拼接不混淆、非 ASCII 理由、同内容新操作新 ID、复制/注释/replace 不改 ID；删缓存后仍可复算普通记录，Git 历史丢失则明确失败。

### E-3：单次发布、锁与中断结果（ED-08～10；OQ-P7）

- 每个元数据目录使用固定文件上的 OS 独占锁，使用 Rust `File::try_lock`；冲突立即拒绝，不等待后偷偷重读重试。PID/时间只供诊断，不是锁是否有效的依据。进程退出由 OS 释放锁，不新增基于“看起来陈旧”的强制 unlock 产品命令。遵守同一协议的 OMD 写入才受此保护；手工编辑文件和外部编辑器不被锁阻止。
- verify/check 返回 `--expected` 可使用的观察凭据：相关存储发布代号、节点 tip、来源 hash、采集版本及登记修订。写操作在持锁后逐项核对；旧 tip、来源或登记不匹配即拒绝，不换成新值。人和 AI 使用相同前置条件。直接 init 的“目标尚未登记”是前置条件；已有对象更新须携带其观察依据。
- 一次来源采集只运行一次。成功采集的完整字节和来源版本可持久保存并返回引用，不自动创建正文 commit 或确认标记；相同已有内容不为“最后检查时间”反复写记录。失败/取消的临时 stdout 不进入成功版本。后续 commit 使用该版本；文件写前重新读取核对观察 hash，command 不因核对再执行。文件最终读取后仍可能被外部程序修改，不承诺阻止外部编辑，下一次观察继续检测。
- 登记、binding 和 inbound 的每次修订同样写成新不可变记录，由 state 指向所选修订；不得原地覆盖旧 state 仍引用的文件。所有读取先固定 state，再沿其引用读取，不能混读目录中“最新文件”。普通读取完成前复核参与目录的发布代号；变化则返回 conflict/incomplete，不以混合快照宣布通过。
- 单次逻辑更新先在同一文件系统写齐不可变记录/内容并 sync，再写新 state 到临时文件并 sync，原子替换 state 后同步目录。只有新 state 引用的记录计为本次发布。旧 state 未切换则旧有效状态保持；切换后响应丢失，重启能据 state 中的 operation ID 判断实际已发布，不重跑命令或重建一条同操作提交。写入后同步失败报告结果不确定及 operation ID，而不假称“什么都没发生”。
- pending 与未被任何已发布 state 接纳的孤立文件不冒充 dangling 的历史 commit。state 显式保留所有尚未 gc 的已发布记录 ID 清单，reset 只移动 tip/挂载，不从该清单移除历史；由此无需猜测磁盘文件曾否发布。普通查询只诊断，不自动发布或删除；显式 gc 可核对后清理未发布材料。操作发生前的版本冲突不留下部分业务结果。
- ATOMIC 组合按 begin、普通成员、新 link、end 逐次经过上述发布点，每次成功立即生效。参数重复/语法错误在 begin 前全部检查；之后第 k 步 I/O 失败，保留前 k-1 步，不补 end。输出实际成功 ID、失败步骤及开放边界；用户显式继续或 reset。嵌套用同链标记栈识别，begin/end reset 始终只退直接前驱；文件 reset 先检查全部子目标，再一次发布，拒绝时零部分恢复。
- 必须在承诺支持的平台/文件系统上验证锁、同目录替换及目录持久化；仅有 `write_all` 或 rename 不足以宣称掉电安全。不满足这些能力时拒绝写入，不退化成覆盖写。SQLite 随后更新，失败只使缓存失效，不撤回已发布业务记录。

### E-4：跨目录引用与 GC 保护（OQ-P6；保持单链 ATOMIC）

不合并 A/B 存储，不建立跨项目业务提交链。每条 link/适配/其他必要引用有唯一业务记录所属目录；被引用方只持久保存保护凭据，用于反查及防止误删，不能作为第二份 link 权威记录。

1. 显式登记本地 peer 定位，检查其存储身份与项目映射；操作枚举全部必要依据涉及的目录，按规范绝对路径排序尝试加锁，任何锁/版本失败则释放并拒绝。发现新的依赖目录要重新构造读集合并由用户重新确认依据，不在持有部分锁时无界追锁。
2. 拟写入 A 的记录需要 B 中版本 b1 时，先在 B 持久发布 inbound 凭据，包含 A 的登记身份/定位、预计算的记录 ID 及 b1 等确切保护目标；再在 A 发布业务记录。B 凭据成功但 A 未发布时，只多保留数据，不算 link 已建立；查询两端均须读取 A 的实际有效创建记录。该顺序不等于分布式业务事务或 ATOMIC 整块发布。
3. A 的记录 reset 后，业务效果由 A 的有效链立即决定；B 上的凭据不赋予被撤下记录有效性。reset 不主动删除保护凭据。B gc 若可读 A，则核对有效记录与需保留的传递依据；若 A 不可用，保守保留对应对象并报告阻塞，不以缓存、超时或用户删除 alias 为理由释放保护。孤立凭据只有在确认 A 未发布/已无保护需要后，由显式 gc 回收。
4. gc 从本地有效挂载根以及仍生效或暂不能核验的外来保护目标出发，遍历 previous_id、版本、link/适配依据、块结构依据及所需完整内容，保留传递闭包。只有不在保护集合中的记录才可清理；清理 commit 时连同其 note，仍被别处共享的内容不删。对仍保留且须复算的历史也保留必要输入。跨存储 gc 同样锁定本次核验目录，先完成判断再本地删除。
5. 对方的 Git 历史可读性不由 OMD 锁保证；缺 Git 对象照常报错，不能借 inbound 凭据宣称已保护 Git 对象不被用户 gc。OMD 不自动创建 Git protective ref。

**失联取舍：** 正常本地读写仅核对其实际依赖的 peer，不因无关项目离线阻塞。涉及离线依据的查询返回不完整诊断，不报告“没有 link”或成功覆盖；gc 只跳过无法证明安全的候选并明确列出原因。移动存储需显式更新 peer 定位并保持 store_id；把副本用作另一可写权威目录时，须显式登记为副本、分配新的 store_id，保留 project_id、原 commit 输入与 ID，并先登记复制后仍有效或需保护的外部引用。不能因复制文件就假定对方已知道新的消费者地址；未完成登记时只允许历史诊断读取，不发布新的业务更新或执行 gc。此方案宁可暂时多保留，不靠自动拉取、缓存主副本或超时删除恢复可用性。

### E-5：本地解析、Git 历史与 replace（ED-04、13～15；OQ-P6/P8/P9）

- 既有 `proj:<alias>:<path>` / `proj:<alias>:byte::<path>` 在固定前缀后将剩余输入当作完整路径，不全局分割 `::`。路径只用 `/`；command 在固定 executable 分隔符之后把剩余内容完整交给 JSON argv 解析器。撤回统一 `\::` 转义的旧 ED-04 候选；需要包含分隔符的 executable 或其他不能无歧义表达的字段时使用 `--source-json <JSON 对象>`，不引入变量模板或 shell 拼接。
- Git 历史引用为 `git::<JSON 对象>`，字段 `{repo, commit, path}`；repo 是显式本地仓库定位，commit 必须为完整精确 Git commit ID，path 为该版本内路径。使用 Git 对象读取而非 diff/index，验证对象类型，取完整 blob；不启用 textconv/filter，不允许 partial clone 隐式 lazy fetch。记录必要 Git 定位和内容 hash，浮动 ref 不写入历史。Git 路径中的符号链接按树中目标在同一提交内解析并检测循环/断链，不能转而读取工作树冒充历史。
- `omd replace <有完整来源依据的 commit-id> --source <引用> --expected <凭据>` 选择该记录引用的完整来源版本；元数据操作没有来源依据时拒绝，不能猜“最近一个文件”。新 file/command 来源采集成功后保存完整字节，Git 来源验证确切对象；完整字节相同才替换该版本的恢复 binding，不新增 OMD commit。引用同一版本 ID 的记录共同使用该 binding，结果须列出受影响记录；不同版本即使内容 hash 相同，也不批量改绑。
- replace 显式指向 command 时，授权该次固定命令采集一次，与显式 init 一样；不借 verify/check 的开关替代此授权，也不在以后恢复历史时重跑程序。成功与失败仍遵守完整 stdout/项目根/原绑定不变等规则。**replace 作用域仅为所选已记录版本的恢复方式**：不改当前观察定义；真实文件当前仍读登记路径，虚拟 command 当前仍按其许可采集。原始操作输入仍保留最初的来源描述，新的恢复定位另存，不改写原始输入。
- replace 不自动删除旧副本。释放入口为显式 `omd gc --content`：仅清理没有任何仍需本地副本的保留记录引用的内容；在释放 Git 替代的最后一份本地内容前重新核验其 Git 恢复依据。O0:Z 没有替代时保留 Z，其他记录共享 X 且仍要求本地存储时保留 X。缺失替代依据则拒绝释放，不自动 fetch。
- alias 的显示名/本机路径可显式修正，但引用固化为存储身份、范围首提交 ID 和必要版本 ID，不跟随字符串同名换绑。登记不可读或身份不符报错；只查看登记/历史的诊断入口仍可用来纠正错误，不要求先联网。可选 remote 校验要求明确 remote 名，比较未经猜测转换的配置 URL；等价的 SSH/HTTPS 等写法由显式映射认可，不自动丢用户名、路径大小写或端口。
- 配置路径按 OMD 专用环境变量优先；空字符串视为未指定，相对路径相对调用 cwd。项目根选择：显式 `--root` > 本机已登记且包含 cwd 的最深项目根 > 向上最近可识别 OMD 结构；不用 Git 猜根。元数据选择：显式路径 > 本机该项目映射 > 根下 `.omd/` > 根直属子目录中唯一 manifest。显式位置错误不回退，多候选报歧义，不全项目递归搜索。不存在的目标只有显式初始化可创建。

### E-6：操作选择、执行器与输出（ED-16～18）

- `commit --id <range-commit-id>` 继续表示范围版本，不挪作 link 选择；普通写入只接受有效当前 tip 作前驱。`--range start:end` 修改或新建范围；`commit atomic begin/end --id <当前范围提交>` 选链，end 配对最内层 begin。组合命令在已有块内可开自己的内层块，成功只关闭自己打开的块。新范围加 link 的组合以 BEGIN 为该新链的首提交，尚无正文成员时不贡献覆盖；若 reset 这个无前驱的 BEGIN，结果为空链并撤下该范围挂载，`actual_id=null`，不编造前驱，也不等同于 reset 虚拟根。这个初始化边界约定已随工程包在 D-33 获得接受。
- 适配语法为重复 `--adapt '<JSON 对象>'`，每项固定字段 `{link_id, changes:[<确切变化commit-id>], reason}`；空理由或未明确选择变化拒绝。源端 clean 用重复 `--stop '<JSON 对象>'`，对应 `{link_id, changes:[...]}`，并提供 `--reason` 或明确 `--no--reason`。不从任意 reason 字符串推断 link，不把同端点 link 合并；--link-from/--link-to 只负责显式新建。
- `--expected <JSON 凭据或文件>` 与 `--timestamp <RFC3339>` 是所有相应写操作的共同参数。完整 ID 或在已选上下文中唯一前缀；跨存储定位用 `--store <本地登记名>` 明确上下文。旧版本可 log，但不能仅因可读就作为写入依据修复 broken。裸 log 为当前存储全部保留提交，按时间倒序、同时间按 ID 稳定排序；tree 仍只表示挂载，不把跨存储 link 变成子节点。
- command 使用直接进程 argv、stdin 关闭为 EOF、继承调用者环境/PATH，不持久保存秘密环境值。含相对目录的 executable 按所属项目根解析，裸 executable 按 PATH 查找；cwd 始终项目根。stdout 与 stderr 同时排空以免死锁；stdout 流式暂存，不静默截断。初版不增加任意默认超时或输出截断阈值；磁盘/启动/读取失败或用户取消均失败，完整退出 0 才接纳。失败不抵消已经发生的外部副作用，不重新运行来确认版本。
- JSON envelope 保留 `{ok, data, diagnostics}`，加入 `schema_version`；诊断至少含 `kind, severity, message, store, node, commit_id`。缺字段用 null，ID/大整数为字符串。检查项给出 `pass/fail/skipped/incomplete` 结果，不是范围生命周期。覆盖输出有来源/单位、covered/total、百分比及 gap 坐标；不能获取当前来源时该项 incomplete、百分比 null，不能当 total=0。边界 reset 输出 `requested_id, actual_id` 及 warning；组合失败输出已成功 ID、失败步骤、开放边界、operation ID。
- 退出码：0 本次请求成功（warn 不单独失败），1 检查不通过/不完整，2 用法/格式错误，3 版本冲突，4 锁冲突，5 I/O/执行失败。JSON 只写 stdout，诊断性进度写 stderr；来源 stderr 不混入 JSON 文档。commit 发布成功但缓存失败可返回成功并 warning，不能假称业务未生效。
- 可选 hook 仅调用正常 verify/check，不读取 Git index；不在本轮安装。将来安装发现已有 hook 时不自动拼接脚本，先让用户显式安排组合，避免修改未知 shell 程序。

### E-7：最小模块及验收顺序（ED-19）

后续实现采用一个 Rust package，library + `omd` binary；库内按记录/存储、来源/差异、关系/检查三个职责分模块，CLI 只解析参数与输出，不提前拆多 crate、服务或后台队列。先固定 schema/hash 黄金向量与文件写入故障注入，再实现普通 file 的 init/commit/verify/check 垂直链路，再加 link/reset/嵌套块，最后接 command、Git/replace 与跨存储引用。SQLite 必须可删除重建；所有关键语义另通过 CLI JSON 的黑盒场景核对。

验收包含：每个单次发布点前后中断、响应丢失、锁冲突/旧凭据、A/B 引用中途失败与离线 gc、多对同端点 link、嵌套标记相邻时退一步、父文件拒绝内部恢复、command 不重复执行、Git 历史丢失、空白仅影响覆盖和删缓存后恢复。实际测试命令、平台及未验证项由实现阶段报告；此处没有运行 Rust/Lean 工程。许可证、发布和可选 skill 交付不因本工程契约被接受而纳入本次实施，Lean 不用于证明锁或并发。

### E-8：工程依据与已知代价

- Rust [`File::try_lock` / `sync_all`](https://doc.rust-lang.org/std/fs/struct.File.html) 提供锁冲突及持久化基础；锁对非参与写入者的作用因平台而异，不能把它宣称为所有工具都遵守的系统事务。[`rename`](https://doc.rust-lang.org/std/fs/fn.rename.html) 有同文件系统等约束，不单独证明跨平台掉电原子性。
- [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785.html) 规定确定性的 JSON 属性排序及原值表示，避免自行发明不明确的 canonical JSON；存储 TOML 的排版不参加 ID。
- [`git cat-file`](https://git-scm.com/docs/git-cat-file) 区分原始对象读取与 filters/textconv。实际实现须禁用可触发外部转换或远端获取的模式；本轮只查文档，没有执行用户来源命令。
- 为保持最小方案，本地 state 更新可重写整个小型索引，跨存储核验可能需要读取多目录；先确保确定性与无误删，不提前引入服务/自动合并。离线引用保守多保留会占空间，这是安全取舍，不暗中设过期策略。

## Risks / Trade-offs

- **纯位置变化也要复核，操作量可能增大。** 缓解：提供候选位置和可显式选用的固定英文理由，不偷换成自动语义放行。
- **将 clean 做成永久节点布尔值会掩盖后续变更。** 缓解：只对具体变更与选定作用域有效，继续遵守旧 hash 冲突即拒绝。
- **推进全局文件基线可能抹掉其他分支的未完成事项。** 缓解：保留未处理关系的确认依据与可恢复内容；具体布局与绑定规则见 E-2/E-5。
- **把 clean 当作完成盖章，会迫使适配提交后再重复确认。** 缓解：按 D-03/D-07 区分提交接续与源端阻断，按 D-08 显式选择所处理的上游变化；具体选择参数按 E-6，不能凭任意 commit 清除所有影响。
- **reset 后其他节点可能引用悬空提交。** 按 D-14 报 broken（脏）并提示 reset 到依据完整的 commit 后重建；不能因数据仍在磁盘而通过，不能用 clean 绕过，也不自动修改源文件或恢复悬空提交。根索引、发布与安全清理按 E-2～E-4 实现并进行故障注入验证。
- **评论或理由修订与状态操作混淆。** 缓解：note 只作外挂说明；commit clean 即使省略理由也仍是显式状态操作，两者不能相互冒充。
- **固定 command 参数不保证输出稳定或没有副作用。** 缓解：verify 默认不执行并遵守显式配置/参数；显式初始化按 D-28 采集一次，同次已采集版本用于后续复核，不为 hash 校验重复运行。
- **持续 import `.omd/` 可能使自身写入产生新变化。** 明确保留这一代价：不得隐藏排除、自动确认或承诺自引用必然收敛。
- **Git remote 身份核对可能失败。** 保持可选身份约束与核心分离；force 已取消，缺失 remote、URL 比较及别名更新按 E-5 和 local-project-links 执行，不能静默接受不匹配。
